## 2. Hard Constraints

```
- НЕ запускать full pipeline без подтверждения
- НЕ трогать /api/client/statistics/json без подтверждения
- НЕ отправлять Telegram без --dry-run
- НЕ менять Render без подтверждения
- НЕ включать auto-actions
- НЕ делать full daily rerun по partial dates
- НЕ начинать recovery с batch 0, если есть partial progress
- НЕ retry при daily_quota_exhausted в том же quota window
- 429 различать по тексту, не оптом:
    daily_quota_exhausted («превышен дневной лимит», «максимум 2000»)
      — настоящий суточный лимит выгрузок, стоп до сброса окна
    любой другой 429 — вероятный антиспам: поддержка Ozon сообщает, что при
      подозрении на спам запросы отклоняются на несколько минут и включаются
      автоматически. Пауза 60 с, не более 3 попыток, затем стоп с явной
      причиной. Число пауз писать в лог и в отчёт прогона
  (прежнее правило «stop on first 429» останавливало сбор на сутки там, где
   хватало минуты, — уточнено 2026-09-11, это не ослабление)
- db_writes = 0 в dry-run/plan-only
- тип, который НЕ должен попадать в группу, не должен начинаться с её префикса:
  пять мест берут рекламу по startswith("advertising"), поэтому внешнее
  продвижение зовётся external_promo, а не advertising_external. Имя дешевле
  любой проверки
- если в отчёте стоят два числа с разницей, разница объясняется в той же
  строке — или отчёт не выпускается. Скобка с исключением рядом с «расхождений
  0» не объяснение: 2026-09-11 итоги отличались на 13 751,18, а подпись
  говорила, что всё сошлось
- сверка берёт дату не моложе ДВУХ СУТОК: начисления доезжают. Измерено —
  сегодняшняя дельта выросла с 13 751,18 до 264 577,62 за полчаса
- никакого молчаливого else: список типов явный, незнакомый тип попадает в
  прочее И называется вслух в отчёте прогона. Прежний else поглотил unknown_*,
  и витрина считала их, пока мы докладывали, что не считает
```

## 3. Как писать в этот файл

За неделю он разошёлся с реальностью в дюжине мест, а читает его каждая сессия.

1. Утверждение несёт, **чем и когда проверено**: «602 кампании (статусные строки, 2026-09-03)», а не «~1206 units».
2. Непроверенное — **помечать гипотезой**, не подавать фактом.
3. Опровергнутое **не удалять, а помечать опровергнутым с причиной** — иначе версия вернётся через месяц. Образец: отозванный §2 в `docs/ozon_cpc_backfill_plan.md`.
4. Длиннее нескольких строк — в `docs/`, здесь ссылка. **§2 не трогать.**

## 4. Ozon Performance API

```
Одновременных выгрузок с аккаунта: 1   ← КРИТИЧНО (подтверждено retryable_429)
Максимум кампаний в отчёте:        10  (DEFAULT_CAMPAIGN_BATCH_SIZE)
```

**Модель квоты — закрыто первоисточником 2026-09-11** (страница Limits
документации Performance API, приведена владельцем дословно):

```
Одна рекламная кампания = одна выгрузка.
Если в запросе несколько кампаний, это считается как несколько выгрузок.

Выгрузок за 24 часа с аккаунта                 2000
Выгрузок за 24 часа в рамках ОРГАНИЗАЦИИ       2000   ← объясняет отказы
Одновременных выгрузок с аккаунта                 1
Одновременных выгрузок по организации             5   ← в спеке 09-13, в этом файле не было
Дней в выгрузке                                  62
Кампаний в отчёте                                10
Общий лимит ЗАПРОСОВ в сутки                100 000   ← мы тратим ~600
Формула: активные_кампании × 240, но не больше табличного значения
```

Потолок 2000 стоит и на организацию целиком — все кабинеты делят одни 2000
выгрузок, поэтому посторонний потребитель ест НАШУ квоту. 2026-09-05: наших
выгрузок 554, отказ; остальные ~1400 взял кто-то ещё внутри организации.
**Второй ключ не поможет** — он внутри той же организации, вопрос закрыт.

Окно **скользящее** («за 24 часа»), не календарные сутки. Расход считать как
`sum(campaign_units)` по `request_kind='submit'` за последние 24 часа.

Формула на нас не влияет: активных кампаний сотни, 240 × сотни всегда больше
2000, потолок всегда ровно 2000.

С **14.09.2026** Ozon ввёл лимиты на операции с кампаниями (спека, тег Limits;
анонс в чате 08.09): создание и копирование 1000/день, смена бюджета и
стратегии 500/день, добавление товаров 1200/день, изменение ставок 6000/день.
Нас не касаются — мы только читаем статистику; auto-actions выключены.

**Опровергнуто дважды, оба раза нами:**
1. «Потолок 2000, половину выбирает кто-то ещё» (2026-09-03) — верно по сути,
   но объяснение нашлось только 09-11: лимит организации.
2. «Лимит считается в ЗАПРОСАХ, опросы входят» (правка 2026-09-06, отозвана в
   тот же день). Приняли текст отказа за спецификацию. Запросов лимит 100 000.
   Вся ветка про «11 опросов на отчёт» и экономию на опросах — ложный след.

```
CPC:          POST /api/client/statistics/json                          ← в лимите
CPO «Все»:    GET  /api/client/statistics/all_sku_promo/orders/generate ← НЕ в лимите
Selected CPO: POST /api/client/statistic/orders/generate ← singular!    ← НЕ в лимите
              kind: SEARCH_PROMO_ORGANISATION_ORDERS
```

`retryable_throttle` — ждём Retry-After, продолжаем. `daily_quota_exhausted` (body
«Превышен дневной лимит») — стоп до сброса окна. В ledger первый пишется как
`retryable_429` — два словаря на одно понятие.

**Не путать с 429 Seller API** (`api-seller.ozon.ru`, `"code": 8`): там частота
запросов в секунду, отказ транзиентный, повтор осмыслен — `loaders/http_retry.py`.
Правило §2 «stop on first 429» относится к Performance. **И тот же `code 8`
Seller API отдаёт на отключённый метод** (чат 11.09, `/v3/posting/fbs/unfulfilled/list`,
подтверждено представителем Ozon): прежде чем лечить паузами — сверить
версию эндпоинта со спекой, `how-we-work.md`.

`smart_recent_active` — единственный режим в рантайме: **554–642 кампании** на свежих
датах (статусные строки, 08-28…09-02), на августовских планах до 2654 — размер зависит
от даты, а не от режима. Прежние «~1675 / ~1206 units» устарели.

## 5. Recovery Worker — сейчас ВЫКЛЮЧЕН

`scripts/ozon_performance_recovery_worker.py`. Выключен `--skip-recovery` с 2026-09-03,
пока не починен выбор дат.

```
pre  — гейт is_yesterday_cpc_loaded: идёт, ТОЛЬКО если вчера уже success,
       то есть всегда работает со СТАРЫМИ датами. Это НЕ подбор хвоста.
post — подбирает хвост ВЧЕРАШНЕЙ даты, затем уходит в исторический бэкфилл.
       --max-batches-per-run 26, --max-attempts 10, --wait-for-minutes 240
budget guard: used > 1500 — ТОЛЬКО pre. У post порог 1800 (2000 − reserve 200).
```
Опровергнуто 2026-09-03: «max 1 batch per run» и «guard при used > 1500» — верно
лишь для pre-фазы.

**Бэклог в этом файле не вести.** Он строится по статусным строкам и расходится с
данными: 30 дат против 28 у детектора, пересечение 11; 17 реальных дыр воркер не
видит, 19 нормальных качает зря. Прежний список из пяти дат был неверен: 05-24,
05-25, 05-27 по данным в порядке, у 05-27 пять статусных строк, а не «MISSING».
Актуальный список — только детектором: `python3 scripts/ozon_cpc_data_gap_report.py`.

`--ozon-recovery-current-day-only` (в коде есть, в команде Render НЕ включён) сужает
работу до хвоста вчерашней даты, без бэкфилла.

**Дефект резюма многодневных окон — НЕ починен (проверено 2026-09-13).**

```
validate_cpc_resume_progress            строка 1556
resolve_existing_cpc_backfill_progress  строка 2208
```

Обе требуют `date_from == date_to == target_date`. Прогресс по многодневному
окну записывается, но прочитать его невозможно. Пока это так, правило §2 «НЕ
начинать recovery с batch 0, если есть partial progress» физически неисполнимо,
и **включать recovery нельзя**.

Номера строк даны на 2026-09-13 и стареют: в прошлой редакции стояли 1536 и
2188, сместились на 13 и 20 строк. Искать по имени функции, а не по номеру.

## 11. Источники знаний и порядок работы

Появились 2026-09-13. Ответы о методах, полях и лимитах Ozon брать отсюда,
а не спрашивать владельца.

**Спека говорит, что метод обещает; чат разработчиков — как он ведёт себя
на самом деле.** Сначала спека, потом чат, потом живой вызов с `db_writes = 0`.

```

spec/ozon-performance.json   Performance API   47 методов,   97 схем,  v2.0
+ 13 спек чужих ролей (retail, ORD, FBP, перевозчики) — spec/README.md
```

Сняты руками из браузера 2026-09-13/14: `docs.ozon.ru` блокирует машинные
запросы. Как переснимать и как проверить, что снялось то самое —
`docs/ozon_spec_refresh.md`. Обновлять, когда Ozon объявляет новые методы
или меняет контракт; раз в пару месяцев без повода тоже не лишнее. Если
менялись методы, которые мы зовём, — сказать в отчёте, не коммитить молча.

Искать в спеке скриптом по `paths[...]` и `components.schemas[...]`,
имена файлов не менять — на них ссылаются сессии.

### `knowledge/telegram/` — чат разработчиков Ozon

```
knowledge/telegram/ozon-dev-chat.json   37 863 сообщения, 2022-05-13 … 2026-09-13,
                                        без пропусков по месяцам, 30 МБ
knowledge/telegram/README.md            структура, поиск, вложения, обновление
```

Файл **целиком не читать** — искать скриптом: фильтровать `messages` по
подстроке в `text`, возвращать дату, автора, текст. `text` бывает строкой
и бывает списком фрагментов — обрабатывать оба, иначе часть сообщений
потеряется. Ветка обсуждения собирается по `id` ↔ `reply_to_message_id`.
Вложения лежат вне репозитория, на машине владельца.

Экспорт — снимок, сам не обновляется. Переснимать из Telegram Desktop и
дописывать к старому по `id`, не заменять целиком.

Здесь искать: реальные сроки отключения методов, недокументированные
ограничения, ответы поддержки, обходные пути. Проверено на деле: антиспам
Seller API (429 `code 8`, отпускает через 60 с) описан в чате поддержкой
и подтверждён живым вызовом 2026-09-13.


**Если путь согласован и конвейер деградирует — иди и делай, не жди
ответа.** Спрашивай только на развилке, которую не обсуждали, или перед

прогон. Два дня ожидания ответа на «начинать с выкупов?» стоили пяти дат
без базы прибыли.

«Готово» — только о проверенном: выполненная команда с выводом, а не
намерение. Работа в ветке подтверждается `git log main..HEAD`.
