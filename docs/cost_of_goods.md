## На каком ключе стыкуется

Ключи из `marketplace_orders` за 90 дней: 4 622 различных пар
`(marketplace_sku, article)`, выручка `orders_amount_buyer`
803 564 138,00 ₽. `article` у нас — offer_id Ozon как есть, с префиксом
кабинета: F — 3 989, T — 490, S — 143. Поэтому искать надо по всем трём
колонкам файла, а не только по «Идентификатор Ozon».

```
ключ                         найдено ключей        выручка найденных
offer_id, три колонки        4 617 из 4 622 (99,9 %)   803 331 914,00 (99,97 %)
числовой id из файла             2 из 4 622 ( 0,0 %)       572 494,00 ( 0,07 %)
хотя бы по одному            4 617                     803 331 914,00 (99,97 %)
ни по одному                     5 ( 0,1 %)                232 224,00 ( 0,03 %)
```

**Ключ — offer_id.** По нему ни один найденный ключ не указывает на две
строки файла с разной себестоимостью (0 из 4 617): наши ключи — те же
варианты «артикул + размер + вставка», что и строки файла, стыковка 1:1.

**Почему числовой id не работает.** `Внешний идентификатор Ozon` — это
`product_id` Ozon, а `marketplace_sku` в заказах — SKU. Это разные
идентификаторы одного товара. Проверено по `sku_catalog`
(её заполняет `ozon_products_loader` именно из `product_id`): у золотого
артикула в файле стоит `3076903012;737405231`, в `sku_catalog`
737405231 → `F000283615`, 3076903012 → `S000283615`, а в заказах у него
SKU 1300079194. Из 3 228 найденных ключей с заполненным числовым id
совпали с нашим SKU 2, не совпали 3 226. Если когда-нибудь понадобится
числовой ключ — идти через `sku_catalog`, но необходимости нет: offer_id
закрывает 99,97 % выручки.

## Две неоднозначности — описаны, не решены

### `Себестоимость` против `единая`

Различаются в 22 888 строках из 28 965 (советник насчитал 22 893 —
разница в округлении до копеек, сравнивал я с округлением). `единая` —
одно значение на артикул 1С: у 7 413 артикулов из 7 557 оно одно на все
размеры и вставки. `Себестоимость` — своя у каждого варианта: одно
значение на артикул только у 5 033 артикулов.

Пример, артикул Т24301А086 (кольцо с топазом), `единая` 2 921,44 на все
размеры, `Себестоимость` по размерам:

```
размер   15,5     16       16,5     17       17,5     18       18,5     19       19,5
         3 269,40 2 575,42 2 740,23 2 853,01 2 948,43 2 792,28 2 879,04 3 312,78 2 922,40
```

Разброс между размерами одного кольца — до 737 ₽ (28 %). Это вес
металла и вставок по размеру, а не ошибка.

**Что ложится на наши ключи без потерь.** Наши ключи — варианты с
размером (`F000314838-16,5-ТП`), то есть та же гранулярность, что у
`Себестоимость`. Она ложится 1:1. `единая` тоже ляжет (у неё одно
значение на артикул, а варианты одного артикула дают один и тот же
номер), но при этом все размеры получат одну цену, и различие между
15,5 и 19 пропадёт.

Цена вопроса на наших продажах за 90 дней:

```
найденных ключей, где Себестоимость ≠ единая   3 116 из 4 617 (67,5 %)
их выручка                                      425 317 218,00 (52,9 %)
Σ (Себестоимость − единая) × qty                −7 026 683,04
```

То есть себестоимость проданного за 90 дней по `Себестоимость` на
7,03 млн ниже, чем по `единая`: продаются в основном размеры дешевле
«средней». Какую брать — решение владельца; для маржи по SKU по смыслу
подходит `Себестоимость`, потому что SKU и есть размер.

## Решение владельца 2026-09-14 и схема таблицы

**Берём `Себестоимость`, не `единая`.** Фактические продажи за 90 дней по
`Себестоимость` на 7 026 683,04 ₽ дешевле, чем дала бы средняя по артикулу:
покупают варианты легче среднего (меньшие размеры), и `единая` этот
перекос стирает. Наши ключи — варианты с размером, `Себестоимость`
ложится на них 1:1.

**Файл в git не кладём.** `data/cost_*.xlsx` в `.gitignore`
(проверено: `git check-ignore -v` → строка 18).

**Схема** — `sql/20260914_create_article_unit_costs.sql` (заменяет
неприменённую `20260518_*`, у той была модель `article + valid_from/valid_to`
без даты снимка). Единица хранения — снимок:

```
ключ            (offer_id_norm, snapshot_date)
offer_id        как в файле и в кабинете, с регистром
offer_id_norm   lower(offer_id), по нему стыковка
snapshot_date   дата снимка 1С; второй файл ДОБАВЛЯЕТ строки, а не заменяет
unit_cost       «Себестоимость», numeric(14,2)
unit_cost_uniform «единая» — справочно, в расчётах не используется
variant_type    main | select | discount  (префикс F / S / T)
article_1c, size, insert_category, product_kind, metal_fineness, weight_g,
discontinued, source_file, source_row, loaded_at
```

**Регистр — нормализованная колонка, а не сравнение при стыковке.**
Четыре наших ключа отличаются от файла только регистром суффикса
(`-Изгт` / `-ИЗгт`). Выбрана колонка `offer_id_norm = lower(offer_id)` с
первичным ключом по ней, потому что: (а) читатель ищет списком через
`in_`, а регистронезависимый `ilike` в PostgREST списка не принимает —
пришлось бы по запросу на ключ; (б) уникальность на уровне, на котором
стыкуем, гарантирует база, а не договорённость; (в) коллизий по `lower()`
внутри файла нет — 86 799 уникальных до и после. Исходный `offer_id`
сохранён рядом, ничего не теряется. Отклонение от формулировки владельца
«ключ (offer_id, snapshot_date)» — ровно в регистре.

**Выбор снимка при чтении** (`load_article_unit_costs` в
`reports_ozon_ad_diagnostic_rule.py`): последний со `snapshot_date` не
новее даты расчёта; если все снимки новее (сейчас снимок один, 05-20,
а проект с 03-28) — самый ранний, с предупреждением
`cost_snapshot_newer_than_date` в отчёте, а не пустой результат.

**Не грузятся 11 номеров (33 offer_id) с двумя себестоимостями** — список
в разделе «Неоднозначности». Скрипт печатает их поимённо со строками
файла и не усредняет.

**Загрузчик** — `scripts/load_article_unit_costs.py`: без `--apply` только
план (db_writes = 0), с `--apply` — upsert по ключу батчами по 500, отказ,
если за этот `snapshot_date` строки уже есть (нужен `--force`), после
записи — сверка с `marketplace_orders` за 90 дней. План на файле 05-20:

```
строк прочитано        28 965
offer_id получено      86 895 (три колонки), уникальных по lower() 86 799
пропущено              конфликтных 33, дублей с той же ценой 63 (свёрнуты), пустых 0
к записи               86 766 строк: main 28 922, select 28 922, discount 28 922
ожидание сверки        4 621 из 4 622 ключей, не найден F007780899-ТП (26 389,00)
```

**Отчётная прибыль за 2026-03-28 … 09-13 выше на 350 526 604,34 ₽** —

выручку (выручка выкупа ÷ средняя цена заказа за штуку), себестоимость
