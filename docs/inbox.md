предыдущей отчёт уже написан. Файл переписывается целиком, истории в
нём не копится — след остаётся в git.

**Пока задача в работе, советник этот файл не трогает.**

Если задача противоречит правилам из `CLAUDE.md`, выполняется
`CLAUDE.md`, а расхождение описывается в отчёте.

### §2. «% ДРР» Ozon — одна база везде: реклама без НДС / выручка без НДС

Решение владельца 09-29: ДРР считаем от выручки без НДС (после комиссии) — как в формуле образца и в Z сводной. Сводная уже так
(Z = Y / S); статичные листы и утренняя книга — нет:
- `scripts/report_finrez.py:564` `drr_pct = ads_net / turnover_net` → знаменатель = та же выручка без НДС, что S сводной
  (назвать поле в отчёте и доказать равенство S по месяцам); касается «Выкупы Ozon», «Ozon × бренд», «Ozon × категория» — всех
  листов, где считается «% ДРР» Ozon выкупов;
- `scripts/report_ozon_month.py:291` (`_turnover_net`) — так же; это лист «Ozon - месяц» утренней книги Telegram;
- найти `grep`-ом все остальные места, где считается ДРР Ozon (алерт, отчёты 7/60 дней, `report_management`, витрины) — таблица
  «место → числитель → знаменатель → НДС → было/стало за август». Меняем то, что видит владелец в книгах и Telegram; **витрины
  `daily_*` и их пересчёт — только перечислить и предложить, без слова не трогать**. Одна функция на базу (не пять копий формулы).
- «Заказы Ozon» — если там «% ДРР» есть, база «реклама без НДС / сумма заказов без НДС» (выручки у заказов нет); написать, как
  сейчас и как станет.

Справочная колонка **«ДРР по методике Ozon»** (реклама без НДС / оборот с НДС до комиссии — так Ozon считает порог соинвеста) — рядом
на «Выкупы Ozon» и «Ozon - месяц», в сводную не добавлять (форма владельца). В «Примечаниях» — обе базы одной строкой.

Приёмка: «% ДРР» статичных листов = Z сводной по месяцам и итогу, разница 0,0000; Excel-проверка больше не держит эту пару как
«известную разную базу» — берёт в итог; таблица было/стало по месяцам апрель … сентябрь для «Выкупы Ozon» и «Ozon - месяц».

### §3. Цена покупателя FBO — не затирать измеренное при отказе отчёта ЛК

Находка 09-29: отчёт ЛК не пришёл за 180 с (`loaders/ozon_postings_report.py`, `MAX_WAIT_SECONDS = 180`) → `BUYER_COLUMNS`
обнулены на всём 30-дневном окне (2 709 строк, 76,1 % созданного ₽). Сделать в ветке:
- при отказе/таймауте отчёта строки upsert-ом **не переписывают** `BUYER_COLUMNS` (остальные поля пишутся как обычно); новые ключи
  без прошлого измерения — null, как сейчас; предупреждение в алерте остаётся, в нём — число строк, оставшихся со старым значением;
- ожидание отчёта — дольше: предложить число по фактам (сколько секунд отчёт готовился в удачные ночи за последние 14 — из логов
  Render), с учётом общего времени ночи; не больше 600 с;
- тесты: отказ отчёта → старые значения на месте; удачный отчёт → переписаны; новый ключ при отказе → null.
Сухой прогон — на копии строк, не в базе.

### §4. Расходы Ozon по группам финансового отчёта — разбор, без изменений формы

Открытый вопрос пятнадцатой: где граница «логистика / прочее». В переписке аналитика (Даниил, 09.04.2026) группы финансового отчёта
Ozon разнесены так: Продажи и Возвраты → оборот; Вознаграждение → комиссия; Продвижение и реклама → реклама; Услуги доставки →
логистика; Услуги FBO → прочие; Услуги партнёров → эквайринг; Прочие начисления → прочие. Сделать:
- найти, откуда Ozon берёт эти группы (метод API финансового отчёта / отчёт о движении средств или группировка типов операций
  по спеке) — назвать источник; если по API — разовые чтения, число обращений в отчёт;
- таблица по месяцам апрель … август: группа Ozon → сумма (с НДС и без) → наша статья → сумма по нашей статье → разница; отдельно
  типы операций, которые мы кладём не туда, куда Ozon, — с суммами;
- **компенсации** (возмещения за потерю/брак и т.п.) — сумма по месяцам и где они у нас сейчас (в фин. рез не входят — проверить);
  включать ли — решение владельца, вариант с цифрами.
Ничего в форме и модулях не менять — только отчёт и предложение.
