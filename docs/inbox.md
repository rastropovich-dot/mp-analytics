# Входящая задача

Сюда советник кладёт задачу для рабочей сессии. Сессия читает этот файл
и выполняет то, что в нём написано, а отчёт пишет в `docs/outbox.md`.

Порядок: одна задача за раз. Прежде чем взять новую, убедись, что по
предыдущей отчёт уже написан. Файл переписывается целиком, истории в
нём не копится — след остаётся в git.

**Пока задача в работе, советник этот файл не трогает.**

Если задача противоречит правилам из `CLAUDE.md`, выполняется
`CLAUDE.md`, а расхождение описывается в отчёте.

### 1. Сначала закоммитить то, что лежит в индексе — оно не твоё

В рабочем дереве три изменённых файла, их положил советник:

    CLAUDE.md                              строка про объём чата
    knowledge/telegram/README.md           переписан раздел про обновление
    knowledge/telegram/ozon-dev-chat.json  слит инкремент за 13–17 сентября

Коммит не сделан по прозаической причине: в шелле моста, через который
советник ходит на машину владельца, нет git-идентичности, а
подставлять свою он не стал.

Что слито: инкремент 194 сообщения, id 65876 … 66166, пересечение с
базой 156, новых 38, изменились 3 — только реакции. Итог 38 024
сообщения, 2022-05-13 … 2026-09-17, ни один месяц не выпал. Бэкап
перед слиянием — `ozon-dev-chat.json.bak`, инкремент —
`_increment_20260917.json`, оба в `.gitignore`.

Проверь сам, не верь на слово: сообщений в файле, что ни одно старое
не потерялось против `.bak`, и что файл читается скриптом. Если
сходится — коммить отдельным коммитом, до мержа. Если нет — не мержи,
пиши в отчёт.

Одно предупреждение записано в README и стоит того, чтобы его знать:
файл должен храниться с `indent=1` и `ensure_ascii=False`. Компактный
JSON ничего не теряет, но превращает 30 МБ в одну строку, и `git diff`
перестаёт показывать, что изменилось.

### 1а. Вложения чата: дыра была, закрыта, но проверь

Слить JSON мало. Telegram кладёт вложения каждого экспорта в **свой**
корень (`ChatExport_2026-09-13`, `…-09-15`, `…-09-17`), а имена внутри
сквозные — `photo_2555@16-09-2026_10-35-35.jpg`. Путь в поле `photo`
одинаковый во всех экспортах, отличается только корень. README обещает
один корень — 09-13. Значит, после слияния 09-15 одиннадцать вложений
указывали в корень, которого README не знает: файл на диске есть,
а по документированному пути его нет. Дыра держалась два дня и
обнаружилась только 09-17.

Советник её закрыл: перенёс 11 фото (шесть из экспорта 09-15, пять из
09-17) в корень 09-13, столкновений имён не было. После переноса все
2 822 пути из JSON разрешаются под одним корнем, промахов ноль; ещё 73
вложения Telegram не выгрузил из-за размера — у них в JSON вместо пути
текст в скобках, отличать по первому символу `(`.

Проверь это сам тем же способом: пройти все `photo` и `file`, пропустить
начинающиеся со скобки, и убедиться, что остальные существуют
относительно `~/Downloads/Telegram Desktop/ChatExport_2026-09-13/`.
Ожидаемые числа — 2 822 и 73. Правило на будущее записано в README, в
разделе про вложения: при каждом слиянии вложения нового экспорта
копируются в корень 09-13, и он остаётся единственным.

### 2. Потом мерж

    git merge --no-ff orders-cancelled-columns
    git push origin main

Render катит сам. Ветка — два коммита, `e173109` и `3924a8b`; в проде
их нет, проверь `git log main..orders-cancelled-columns` перед мержем и
`git log origin/main -1` после пуша, а не «готово» на глаз.

Порядок именно такой: миграция (сделана) → мерж → ночь. Обратный
порядок ломает загрузчики на первом upsert.

### 3. Что ждать ночью

Сегодня в прод въезжают сразу две новинки — лог статусов отправлений
уехал вчера, колонки отмен уезжают сейчас. Разбор утром по признакам:

* тревога «Шаг не выполнен» у шага заказов с текстом про
  `cancelled_orders_qty` — код ушёл, а схемы нет; но схема есть, так
  что это означало бы, что мержили не ту ветку;
* шаги заказов прошли, блок лога пуст или код 1 — поломка лога
  статусов, к колонкам отношения не имеет;
* шаги прошли, лог записал, `cancelled_orders_qty` везде нули — мерж
  не доехал до Render.

Ожидаемое нормальное утро: в `cancelled_orders_*` появились ненулевые
значения, `observed_at` заполнен у строк Ozon и остался null у WB.
