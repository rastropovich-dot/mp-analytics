# Входящая задача

Сюда советник кладёт задачу для рабочей сессии. Сессия читает этот файл
и выполняет то, что в нём написано, а отчёт пишет в `docs/outbox.md`.

Порядок: одна задача за раз. Прежде чем взять новую, убедись, что по
предыдущей отчёт уже написан. Файл переписывается целиком, истории в
нём не копится — след остаётся в git.

**Пока задача в работе, советник этот файл не трогает.**

Если задача противоречит правилам из `CLAUDE.md`, выполняется
`CLAUDE.md`, а расхождение описывается в отчёте.

## 2026-09-18, двадцать вторая задача: пересборка истории заказов, до плана включительно

Двадцать первая принята. Разбор ночи сделан как надо: ты не приняла мой
критерий «падение `orders_qty` у FBO = поломка» на веру, а проверила по

против лога статусов, совпавшая до рубля по обеим схемам, — это ровно

### 0. Зачем сейчас

Ночь 09-18 переписала окно 30 дней по новому правилу, а всё, что
старше 08-19, осталось по двум старым. Ряд разорван: витрина уже
показывает Ozon 08-18 — 9 910 881 против 08-19 — 7 566 374, и
`ad_share_of_orders` 5,6–6,0 % до границы против 7,7–10,1 % после. Это
смена базы, а не рост рекламы, но объяснять это в каждом отчёте нельзя,
и само не зарастёт. Лечит пересборка.

Инструмент готов — `scripts/rebuild_ozon_orders_history.py`, четыре
режима. Сегодня идём до `--plan` включительно и **останавливаемся**.

### 1. Три шага без записи

```
--estimate                      обращения, время, что перепишется; без API
--fetch  --date-from 2026-03-28 сырьё в data/postings_raw/; файл есть — в API не идёт
--plan   --date-from 2026-03-28 строки по новому правилу против таблицы, помесячно
```

Ориентиры из прежних замеров: ~705 обращений, ~24 минуты, ~56 248
строк. Если `--estimate` даст заметно другое — назови и объясни, прежде
чем идти в `--fetch`.

Сейчас 13:13 UTC, до ночного окна 00:15 далеко. Скрипт сам не стартует в
00:15…03:15 UTC — не обходи эту защиту.

### 2. Что должен показать план — и чем его проверять

`--plan` даёт помесячно «было / станет». Прежде чем показывать
владельцу, сверь с тем, что мы уже знаем, иначе план — просто столбик
чисел:

* **FBS**: старое правило складывало отменённые вместе с подтверждёнными,
  значит сумма пары по каждому месяцу должна остаться примерно прежней,
  а `orders_qty` — упасть. На окне 09-03…09-16 это дало долю отмен
  27,3 % штук / 31,1 % денег;
* **FBO**: старое правило отменённые выбрасывало и оставляло мёртвые
  ключи, значит `orders_qty` упадёт на застрявший остаток, а сумма пары
  вырастет. На том же окне — 29,2 % / 32,1 %;
* доля отмен по месяцам должна расти к плато ~38–41 % на давних месяцах
  (там всё дозрело) и быть ниже на свежих. Если по марту или апрелю
  доля окажется околонулевой — это не «отмен не было», это, скорее
  всего, метод не отдаёт старые отменённые, и тогда пересборка за те
  месяцы бессмысленна. Проверь и скажи прямо.

Отдельно посчитай и назови: **что станет со ступенькой 08-18 / 08-19**
(сейчас 9 910 881 / 7 566 374) — по плану 08-18 должен опуститься в
линию, а не остаться на месте.

### 3. Стоп перед записью

`--apply` — единственный необратимый шаг: снимок, delete за окно по
схеме, запись. **Не запускать.** Скрипт так и задуман — «запускает
владелец». Покажи план, дождись слова.

В отчёте заранее назови две вещи, которые понадобятся сразу после:

* **ключи витрин, у которых заказов не останется** — скрипт витрины не
  трогает, а ночной KPI строит их заново; перечисли, сколько таких
  ключей и в каких таблицах, чтобы чистка не стала сюрпризом;
* **сколько времени займёт `--apply`** и попадает ли он в окно до
  ночного прогона.
