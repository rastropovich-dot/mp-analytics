### 0. Что строим и почему

Твой §7: лист зависит от файлов на диске, потому что типы 41 + 54 в базу
не пишутся, тип 1 растворён в `other`, 51 — в `subscription` вместе с 52 и
74, 96 — в `other`. `marketplace_expenses` под это не переделываем: 290
тысяч строк с ключом по статье, а нужны четыре колонки. Вместо этого —
**леджер по типам**: маленькая таблица «дата × тип начисления → сумма»,
из того же ответа `accrual/by-day`, который загрузчик расходов и так
получает каждую ночь. Все типы без классификации и без `else`: тип
хранится числом, статья — дело читателя.

Решение владельца 2026-09-21 (запиши в `reports_model.md` §1 пунктом 8):
компенсации Ozon (типы 25 и 10) в листе — **отдельной строкой дохода
«Компенсации»**, в расходы и в «Прочее» не входят; рядом справочная
колонка «Фин. рез. с компенсациями» — она и сопоставима с «Фин. рез.»
владельца, у которого компенсации сидят внутри «Прочего».

### 1. Таблица

`sql/20260921_create_ozon_accrual_daily_types.sql`, применяет владелец
(MCP или SQL-редактор — как с логом статусов):

```
ozon_accrual_daily_types
  accrual_date   date         день начисления (как в by-day)
  type_id        integer      тип начисления Ozon
  type_name      text         имя из справочника типов на момент записи
  amount         numeric(14,2) сумма СО ЗНАКОМ, как отдаёт Ozon: списание с продавца < 0, начисление продавцу > 0;
                              никакого abs() и никакого «расход положителен» — знак меняет читатель
  lines          integer      сколько строк услуг легло в сумму
  loaded_at      timestamptz  момент записи
  primary key (accrual_date, type_id)
```

Без SKU — лист дневной, реклама по SKU у нас из Performance (решение 5).
Одна строка на (дата, тип); нулевые суммы тоже пишем — «тип был, но
свернулся в ноль» отличается от «типа не было».

### 2. Ночной шаг

В `ozon_expenses_loader.py` после `save_expense_rows` — из тех же
`accruals` строки леджера через `_service_lines` (все типы, включая 41,
54, 25, 10 и неизвестные) и upsert по ключу. Отказ записи леджера не
должен ронять шаг расходов: `try/except` с печатью и продолжением, как
с сырьём в обёртках заказов. Тесты: сбор из подделки by-day даёт суммы по
типам со знаком; 41/54 и 25/10 в леджере есть, в расходах по-прежнему
нет; отказ upsert леджера не мешает записи расходов.

Ветка `accrual-types-ledger`. Мерж — по слову владельца блоком «вопрос,
задача не закончена», после п. 3.

### 3. История — план, потом слово

Сырьё есть: `data/accrual_history/<день>.json`, 176 файлов 03-28 … 09-19;
09-20 и 09-21 досними тем же путём. Скрипт посева читает файлы, в API не
ходит (есть файл — не снимать), без `--apply` не пишет. Покажи план:
дат, строк (дата × тип), типов всего, из них незнакомых `TYPE_TO_EXPENSE`;
суммы по 41, 54, 1, 51, 96, 25, 10 за период.

**Полнота — внешним арбитром, до копейки на каждой дате:** для каждой
даты Σ по типам леджера, свёрнутая через `TYPE_TO_EXPENSE` в статьи, со
сменой знака, = `marketplace_expenses` по статьям за ту же дату (41/54 и
25/10 из свёртки исключены, у них в расходах строк нет). Даты моложе двух
суток — с пометкой, начисления доезжают. Отдельно: 41 + 54 из леджера за
03-28 … 09-15 = 85 238 544,85 (двадцатая задача) — назови своё число
рядом. Расхождение — в той же строке с объяснением, иначе `--apply` не
запускать.

`--apply` посева — по слову владельца, той же сессией, что показала план;
таблица новая и пустая, чужого не трогает, но правило то же.
