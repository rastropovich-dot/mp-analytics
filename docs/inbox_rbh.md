## 2026-09-28, первая задача RBH: многокабинетность mp-analytics и подключение кабинета «РБХ»

Ветка `multi-cabinet` в worktree `~/mp-analytics-rbh`. Принцип: один код, кабинет = профиль. Каждый кабинет живёт в своём каталоге (свой `.env`, свои `data/` и `logs/`) и в своём сервисе Render — переменные окружения там свои. Выбор профиля — переменная `MP_CABINET` (`karatov` по умолчанию, когда не задана: KARATOV ничего не должен заметить; `rbh` — новый). **db_writes = 0 до слова; к API KARATOV не обращаться вовсе, к API РБХ — только чтение и только в §5 по шагам.**

### §1. Инвентаризация (чтение, отчёт таблицами)

1. Где читается окружение: `SUPABASE_URL` / `SUPABASE_SERVICE_KEY` (≈38 файлов), `OZON_CLIENT_ID` / `OZON_API_KEY` (≈18), `WB_API_KEY` (≈12), `TELEGRAM_*` (≈7), `OZON_PERFORMANCE_*`, `APP_TIMEZONE`, прочие; `load_dotenv()` — 183 вызова. Есть ли общая фабрика клиента Supabase или каждый файл создаёт свой — список мест создания клиента.
2. Где зашит кабинет KARATOV: `SHOP = "KARATOV"` (`report_finrez.py`, `report_finrez_wb.py`), правило бренда по первой букве артикула (`t` → «Топаз», иначе KARATOV — `ozon_product_catalog.py`, `report_finrez_wb.py`), `COST_INDEX`, `OWNER_AFTER_COMMISSION`, снимок себестоимости `cost_20260520.xlsx`, `category_tree.json`, тексты алертов и подписи книг, имена файлов отчётов, `TELEGRAM_CHAT_ID`, всё, что найдёшь grep-ом по «KARATOV», «Топаз», «ГОЛДСТАРТ», «t-» и по датам снимков. Таблица: файл, строка, что это, куда уедет (профиль / env / остаётся).
3. Точки входа: `run_daily_pipeline.py`, `alerts_telegram.py`, все скрипты с `--apply` или записью в базу, `scripts/report_finrez.py`, `finrez_nightly.sh`, команды cron на Render (из логов/CLAUDE.md). Список.

### §2. Профиль кабинета и защита от перепутывания

`cabinet.py` в корне: читает `MP_CABINET` (по умолчанию `karatov`), отдаёт профиль из `cabinets/karatov.py` и `cabinets/rbh.py` — только несекретное: код, отображаемое имя, правило бренда по артикулу, `SHOP`, множители владельца, индекс СС, имя файла снимка СС, путь дерева категорий, префикс имён файлов отчётов, заголовок алерта, **ожидаемый project ref Supabase** (хост из `SUPABASE_URL`, у KARATOV — из текущего `.env`, это не секрет). Функция `assert_env()`: если хост `SUPABASE_URL` из окружения ≠ ref профиля — `SystemExit` с внятной строкой ДО создания любого клиента; вызывается в начале каждой точки входа из §1.3 (пайплайн, алерт, скрипты с записью, книга, nightly). Первая строка лога пайплайна и первая строка алерта — «кабинет: KARATOV» / «кабинет: РБХ». Тесты: профиль по умолчанию — karatov; `MP_CABINET=rbh` — профиль rbh; guard роняет при чужом ref; `assert_env` стоит во всех точках входа (тест grep-ом по списку §1.3).

### §3. Зашитые значения → профиль

Перед этим влить `origin/main` (Ozon-сессия сейчас правит `report_finrez.py` в сорок четвёртой, WB-сессия — `report_finrez_wb.py` в четырнадцатой — дождаться их мержей, спросить владельца строкой «влить main?»). Перенести всё из таблицы §1.2 в профили; поведение KARATOV не меняется: полный набор тестов, плюс тест «в коде вне `cabinets/` и `tests/` литералов KARATOV / Топаз нет». Проверка без изменений: `scripts/report_finrez.py --check` и утренние книги месяцев на `MP_CABINET` не задан и на `MP_CABINET=karatov` — числа те же, что до ветки (сравнить с прогоном на `main`).

### §4. Приёмка ветки и мерж — по слову

Отчёт: таблицы §1, дерево профиля, список точек входа с guard, до/после по §3. Мерж `multi-cabinet` в `main` — по слову владельца; первая ночь KARATOV на слитом коде — по обычному чек-листу Ozon/WB-сессий, для них ничего не меняется (`MP_CABINET` у них не задан).

### §5. Подключение РБХ — после мержа, шаг за шагом, каждый по слову

1. `.env` для `~/mp-analytics-rbh`: выдать владельцу шаблон (имена переменных из `.env.example` + `MP_CABINET=rbh`), заполняет он сам; проверка — `cabinet.assert_env()` и по одному чтению: Ozon (что-нибудь лёгкое — список складов или один SKU), WB `seller-info`, Telegram `getMe`; ответы (без ключей) — в отчёт; ref проекта Supabase — в `cabinets/rbh.py`.
2. База: владелец создаёт пустой проект Supabase; по слову — применить `sql/` в порядке дат (43 файла), затем сравнить `information_schema` (таблицы, колонки, типы, индексы, представления, функции) с KARATOV — расхождений 0, таблица в отчёт.
3. Сухие прогоны загрузчиков РБХ на 2 дня каждый (заказы, продажи, отчёт реализации, воронка WB, реклама WB, остатки; Ozon FBS/FBO, финоперации, начисления, Performance — с учётом квоты): обращения и 429 считать, строки — в отчёт, db_writes 0.
4. По слову — первая запись и история: окно по умолчанию 60 дней назад (владелец может изменить); Performance Ozon — по квоте, несколько ночей.
5. Render: владелец создаёт сервис `mp-analytics-rbh` (cron как у KARATOV, 00:15 UTC), переменные — по списку из п. 1 плюс `MP_CABINET=rbh`; Telegram — тот же бот, новая группа, её `TELEGRAM_CHAT_ID`; первая ночь — чек-лист как у Ozon/WB, отчёт.
