Сюда советник кладёт задачу для рабочей сессии по Wildberries. Сессия
читает этот файл и выполняет то, что в нём написано, а отчёт пишет в
`docs/outbox_wb.md`. Правила обмена те же, что у Ozon-потока
(`docs/how-we-work.md`, раздел «Порядок обмена»): одна задача за раз,
файл переписывается целиком, пока задача в работе — советник его не
трогает; вопрос посреди задачи — в `outbox_wb.md` блоком «вопрос, задача
не закончена».

`docs/inbox.md` и `docs/outbox.md` — канал Ozon-сессии. Не читать как
задачу и не писать туда.

K падает к молодым дням (975 тыс. → 13 тыс.) — это не созданные заказы дня
(у Ozon-блока «Выручка» = созданные × 0,53 / 1,22 по UTC-суткам, тридцать
первая). Догадка советника, **уже проверенная и не подтвердившаяся**: K =
отчёт реализации по `orderDt` (МСК) — по сырью `data/wb_sales_report_raw/`
за 09-01…09-22 оборот по дате заказа 611 120 / 776 138 / 608 309 … и нули на
09-19…09-22, отношения к K не постоянны, на 09-19…22 у него ненули. Так что
источник другой. Кандидаты, каждый — таблица по дням против K и L:

1. `marketplace_orders` WB (созданные по дате заказа, `orders_amount_seller`
   = `priceWithDisc`, `orders_amount_buyer` = `finishedPrice`) — с фильтрами:
   все / без `isCancel` / только с продажей (по `srid` в отчёте реализации —
   когорта «заказ дня D, у которого есть продажа к 09-22»); множители — как
   у Ozon искали: × (1 − кВВ) / 1,22, × 0,475, forPay-подобные.
2. Воронка `marketplace_orders_analytics` (выкупы по дате заказа, если WB так
   их относит — проверить по спеке, не по памяти).
3. `supplier/sales` (`flag=1`, если сырьё есть на диске) по дате заказа.
4. Отчёт реализации по `orderDt`, но с `forPay` / выручкой по формуле листа
   «WB - месяц» — таблица советника показала, что оборот не совпадает;
   привести для полноты одну строку итога, не искать дальше.

Совпадением считать ≤ 1 % на ≥ 18 днях из 22 или точное на всех. Граница —
1,5 часа на K; не нашлось — три ближайших кандидата с разницей по дням, и
стоп.

**Площадки WB — догадка советника, проверить, не принимать на веру.** В
книге владельца K листа «Заказы» = 'Заказы Standard'!K + 'WB Дискаунтер'!B
(09-01: 863 109,41 + 112 516,20 = 975 625,61), то есть WB у него делится на
«Standard» и «Дискаунтер». У Ozon площадка — первая буква артикула (F —
основная, S — Селект, T — Дискаунтер, `reports_model.md` §6); в WB-сырье
артикулы `f…` и `t…` тоже есть (`vendorCode` `t000066064`). Проверить на
заказах и на продажах: даёт ли деление по букве `t` числа его «WB
Дискаунтер» (B 112 516,20 / 163 626,56 за 09-01/02, C «Маржа» 14 125,41 /
31 002,66). Если да — это ключ и к K. Реестр дыр: `docs/owner_workbook_gaps.md`
в `main` (дыра 4), после мержа `main` в ветку — ставить статус там.

**P «Соинвест, %».** По инструкции владельца соинвест WB = (priceWithDisc −
finishedPrice) / priceWithDisc. В отчёте реализации есть поле `spp`; советник
посчитал Σ `retailPriceWithDisc × spp` / Σ `retailPriceWithDisc` по
`orderDt` (Продажа − Возврат): 09-01 0,428, 09-02 0,429, 09-03 0,431, 09-04
0,434, 09-05 0,433, 09-06 0,433, 09-07 0,421, 09-08 0,384, 09-09 0,386 … 09-18
0,364. С P сходится в первую неделю (кроме 09-03: у него 0,19), дальше
расходится (09-08: 0,44 против 0,384). Значит P — не из отчёта, а скорее
из заказов. Посчитать из `marketplace_orders` WB по дню заказа:
(`orders_amount_seller` − `orders_amount_buyer`) / `orders_amount_seller` —
все и без отменённых; и то же по `saleDt`. Таблица против P; 09-03 = 0,19 и
09-14 = 0,28 — либо его рука, либо в источнике провал в тот день — сказать,
что говорят наши данные за эти два дня.

Результат §2 — только числа и вывод «K = …, P = …» или «не найдено»; лист
«Заказы WB» в генераторе — следующей задачей, после решения советника.

### §3. `marketplace_buyouts` WB из отчёта реализации — план, без записи

Пятая показала: апрель–август `marketplace_buyouts` ниже отчёта на 8,66 млн,
февраль–март базы нет, сентябрь равен. Подготовить замену источника:

1. Сверка по дням 03-26…09-22: `buyouts_qty` и `buyouts_amount_seller` из
   `marketplace_buyouts` против отчёта реализации (Продажа − Возврат) в
   двух разрезах даты — `saleDt` МСК и `rr_date`; сказать, какой из них
   нынешний загрузчик `supplier/sales` использует как дату (по коду и по
   совпадению сентября 21/21). Таблица по месяцам: строк, шт, ₽, разница;
   дни с разницей > 1 % — списком с причиной класса (недобор старого окна /
   возврат в другой день / иное).
2. Скрипт `scripts/wb_buyouts_rebuild_from_report.py`: `--plan` — что
   изменится по дням (добавить / переписать / удалить), из таблицы
   `wb_sales_report_rows`, без обращений к API; `--apply
   --approve-wb-buyouts-write` — запись; в этой задаче **`--apply` не
   запускать**. Ключи `marketplace_buyouts` WB, которых в отчёте нет, — в план
   на удаление отдельным списком с суммой (это те же «застрявшие», что чинили
   у Ozon).
3. Что делает ночной шаг после замены — предложение: «WB: загрузка
   продаж/выкупов» пишет выкупы из отчёта реализации (окно 21 день, уже в
   базе) вместо `supplier/sales`, или `supplier/sales` остаётся для молодых
   дней (D и D−1, которых в отчёте ещё нет — отчёт D появляется D+1). Оценить
   по данным: сколько ₽ выкупов дня D видит `supplier/sales` в ночь D+1, чего
   отчёт ещё не отдал. Решение — советника после чисел; код шага не менять.

### §4. Решения советника

- Дата листа «WB - месяц» — `saleDt` МСК, как найдено; не пересматривать.
- Комиссия в листе — Σ цена × кВВ строки; «удержано из выплаты всего» —
  справочно. Закрыто.
- Февраль–март выкупов WB в базе нет — восстановление из отчёта войдёт в
  план §3 (02-01…03-25), решение о записи — по слову.
- Лист «WB - месяц» в утреннюю книгу Telegram — не в этой задаче:
  `send_ozon_month_report.py` — файл Ozon-потока, задание туда даст советник.
