## Разбор провала: история заказов WB осыпается

Причина не в пересчёте. Пересчёт лишь показал то, что уже произошло в
`marketplace_orders` за две ночи между прошлым пересчётом и этим.

**Механизм.** `loaders/wb_orders_loader.py`:

```python
params = {"dateFrom": (date.today() - timedelta(days=days_back)).isoformat(), "flag": 0}
```

`flag = 0` в WB Statistics API означает отбор по **дате последнего изменения**, а
не по дате заказа. То есть ответ содержит все заказы, у которых `lastChangeDate`
попал в окно, — включая старые заказы, которых недавно коснулись.

Дальше `save_wb_orders` собирает агрегат по `(order_date, marketplace_sku)`
**из того, что пришло в этом ответе**, и делает `upsert`, то есть **замещает**
хранимое значение, а не дополняет его.

Итог: если у даты 2026-07-24 недавно изменились 3 заказа из 286, ответ содержит
эти 3, агрегат по их SKU пересобирается из трёх строк и **затирает** прежние
полные значения по этим SKU. Каждую ночь старые даты теряют часть заказов.

**Независимое подтверждение.** `marketplace_orders_analytics` (витрина WB Sales
Funnel) пишется один раз на следующее утро после даты и больше не
перезаписывается. Сравнение:

| дата | funnel, шт | marketplace_orders, шт | разница |
|---|---:|---:|---:|
| 2026-07-16 | 292 | 188 | −104 (−36 %) |
| 2026-07-21 | 342 | 160 | −182 (−53 %) |
| 2026-07-24 | 516 | 278 | −238 (−46 %) |
| 2026-08-03 | 292 | 197 | −95 (−33 %) |
| 2026-08-04 | 335 | 286 | −49 (−15 %) |
| 2026-08-07 | 304 | 281 | −23 (−8 %) |
| 2026-08-08 | 267 | 269 | **+2** |
| 2026-08-10 | 222 | 218 | −4 (−2 %) |

Оговорка: это два разных эндпоинта WB с разными определениями, и совпадать
в ноль они не обязаны. Но **разрыв монотонно зависит от возраста даты** — от
нуля на неделе до минус половины на месяце. Разница в определениях давала бы
примерно постоянный сдвиг, а не градиент по возрасту. Градиент — подпись
осыпания.

Реальными отменами это тоже не объясняется: отмены накапливаются за дни, а не
линейно в течение месяца, и не дают 46 % на месячной дате при 0 % на недельной.

**Следствие.** Вся история заказов WB старше окна занижена, и занижение растёт
с возрастом. Снимок, снятый сегодня до пересчёта, уже содержал осыпавшиеся
значения — вернуться к «правильным» числам по нему нельзя, он фиксирует
состояние, а не истину.

**Что чинить (не сделано, отдельная задача).** Либо `flag = 1` — отбор по дате
заказа, тогда ответ по окну полон; либо не замещать агрегат, а пересобирать
день целиком, запрашивая его отдельно. Первое проще и, судя по документации WB,
правильнее по смыслу. До починки любые сравнения WB «месяц к месяцу» и
«неделя к неделе» на исторических датах смещены.

## Про сдвиги Ozon

Ozon двигался в пределах окна перезагрузки (2026-08-03 … 08-30) и по мелочи:
от −1 до −6 заказов в день, крупнейший — 2026-08-04, −132 047 ₽. Это обычное
поведение: статусы отправлений меняются, часть заказов отменяется. Аномалии тут
нет. Признака осыпания, как у WB, тоже нет: сдвиги не растут с возрастом даты и
за пределы окна не выходят.
