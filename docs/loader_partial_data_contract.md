# Предложение: контракт неполноты для восьми «молчунов»

> Только предложение. Ничего не изменено, решение за владельцем.
> Написано 2026-09-03 по итогам аудита из `34ea2e1`.

## Проблема

Восемь загрузчиков ночного пайплайна на не-200 печатают сообщение и возвращают
то, что успели собрать. Шаг завершается с кодом 0, пайплайн идёт дальше, витрина
строится на неполных данных, и **нигде не остаётся следа**, что она неполная.

Это тот же дефект, что мы ловим всю неделю в других местах: `run_status = success`
при нулевой записи (снят в `661b658` проверкой после записи), гейт органики по
пустому бэклогу, «проверка Selected CPO проходит на отсутствии данных».
Правило одно: **отсутствие данных не должно выглядеть как успех.**

Это не теория. Три живых случая:

1. **WB stocks сломан 51 день.** `wb_stocks_loader` получает `404` от
   `statistics-api.wildberries.ru/api/v1/supplier/stocks`, печатает «Ошибка WB
   stocks API», пишет ноль строк, шаг рапортует «✅ Готово». В `stock_daily`
   последняя запись по WB — **2026-07-14**, тогда как по Ozon — 2026-09-01.
   Похоже на снятый с эксплуатации эндпоинт, но проверять это никто не начал,
   потому что ночь была зелёной.
2. **Ложная тревога по выкупам WB 2026-09-02** — разобрана отдельно: витрина за
   09-01 не построилась, алерт прочитал заглушку и объявил падение выкупов на
   100%, хотя выкупы лежали в `marketplace_buyouts`.
3. **Бесконечный цикл по 429** в `wb_sales_funnel_orders_loader` (ограничен в
   `34ea2e1`).

## Что предлагается

### Три состояния вместо одного

| состояние | когда | что значит для витрины |
|---|---|---|
| `success` | все страницы получены, все строки записаны | данные полные |
| `partial` | часть страниц не далась после ретраев | **данные неполные**, известно сколько и где |
| `failed` | не получено ничего | данных нет |

Сейчас все три дают код 0 и неотличимы.

### Куда пишется признак

Новая таблица `daily_source_load_status` — родная сестра
`ozon_performance_daily_load_status`, которая уже делает ровно это для CPC:

```
load_date          date       -- когда шёл прогон
marketplace_code   text       -- 'wb' | 'ozon'
source             text       -- 'wb_sales', 'ozon_fbs_orders', ...
target_date_from   date       -- окно, которое загрузчик перезаливал
target_date_to     date
run_status         text       -- success | partial | failed
pages_attempted    int
pages_succeeded    int
rows_written       int
first_error_status int        -- 404, 429, 500 ...
first_error_preview text      -- первые 280 символов тела
created_at, updated_at
unique (load_date, marketplace_code, source)
```

Почему отдельная таблица, а не поле в существующих: у загрузчиков нет общей
таблицы данных, зато у всех одинаковая форма прогона — окно дат, страницы,
строки. И это позволяет не трогать схемы витрин.

Важно: писать статус **после записи строк**, а не после скачивания. Ровно тот
урок, что закреплён в `661b658`.

### Кто читает

`alerts_telegram.py`. Гейт полноты там уже есть — но только для Ozon
(`ozon_daily_sku_organic_missing`, `partial_ads`, `pending_429`). Расширить его
на источники: если за целевую дату хоть один источник маркетплейса `partial` или
`failed`, управленческий вывод по этому маркетплейсу не строится, как сегодня не
строится по Ozon. Правило «WB не отключается из-за Ozon» сохраняется — статусы
раздельные по `marketplace_code`.

### Что увидит утренний алерт

Сегодня на месте сломанных данных появляется правдоподобная бизнес-новость:

```
⚠️ Главный риск
WB: выкупы вчера ниже среднего 7 дней на -100%
🎯 Что проверить сегодня
— Проверить WB: причины снижения выкупов, отмены, возвраты и проблемные SKU.
```

Стало бы:

```
⚠️ WB вчера: данные неполные, управленческий вывод не строим.
Причины: wb_sales partial (429 на странице 3 из 5, записано 1200 строк),
         wb_stocks failed (404, записано 0 строк).
```

Разница принципиальная: первое отправляет владельца искать отмены и возвраты,
которых нет. Второе называет причину.

## Что конкретно будет по каждому из восьми

| загрузчик | форма запроса | состояние при отказе | что попадёт в статус |
|---|---|---|---|
| `wb_orders_loader.py:32` | один запрос на окно 30 дней | `failed` — всё или ничего | `pages 0/1`, окно, код |
| `wb_sales_loader.py:32` | один запрос на окно 30 дней | `failed` — всё или ничего | то же |
| `wb_stocks_loader.py:31` | один запрос, срез на сейчас | `failed` | **уже сейчас был бы failed 51 день подряд** |
| `wb_sales_funnel_orders_loader.py:85` | страницы внутри дня, дни по одному | `partial` — часть дней/страниц | какие дни не дались |
| `ozon_fbs_orders_loader.py:67` | страницы, `return` накопленного | `partial` | страница, на которой оборвалось |
| `ozon_fbo_orders_loader.py:75` | страницы, `break` | `partial` | то же |
| `ozon_finance_transactions_loader.py:67` | страницы, `break` | `partial` | то же |
| `ozon_expenses_loader.py:86` | страницы, `break` | `partial` | то же |
| `ozon_stocks_loader.py:242` | пачки SKU, `continue` | `partial` — **худший случай**: пропускает пачку и идёт дальше, поэтому число строк выглядит правдоподобным | сколько пачек пропущено |

## Какие ночи из зелёных станут частичными

Честный ответ: **точно сказать нельзя, потому что мы этого не записывали** —
в том и дефект. Что известно:

- **WB stocks — каждая ночь начиная примерно с 2026-07-14.** Это около 51 ночи,
  которые сейчас зелёные и станут `failed` по одному источнику.
- **WB sales funnel** — 429 случаются регулярно, один виден в логе 2026-09-02
  в 00:16:24. Они изживались повтором, так что это `success`, а не `partial`.
- **Остальные шесть** — за неделю доступных логов Render ни одного не-200 не
  видно. То есть массового покраснения ожидать не стоит: скорее всего
  добавится один устойчиво красный источник (WB stocks) и редкие частичные ночи.

Ретраи из `34ea2e1` при этом работают в ту же сторону: транзиентные отказы
теперь чаще изживаются и до статуса `partial` не доходят.

## Порядок, если решим делать

1. Миграция таблицы.
2. Общий помощник записи статуса (по образцу `save_daily_load_status`).
3. Подключить к загрузчикам по одному, начиная с `wb_stocks_loader` — там
   результат виден сразу и подтверждается независимо (`stock_daily` пуст по WB).
4. Только потом расширять гейт в `alerts_telegram.py`, иначе первая же ночь
   даст лавину предупреждений без возможности их проверить.

## Чего предложение НЕ делает

Не превращает `partial` в падение шага. Пайплайн должен доходить до конца и
строить всё, что можно построить, — падение мы как раз лечим отдельно
(развязка fatal, ретраи). Задача этого контракта в том, чтобы неполнота была
**видна**, а не в том, чтобы она останавливала работу.
