# Отчёт рабочей сессии

Сюда рабочая сессия пишет результат по задаче из `docs/inbox.md`.
Советник читает этот файл сам.

Что должно быть в отчёте:

- что сделано, с номерами коммитов
- что НЕ сделано и почему
- числа, а не оценки: сколько строк, сколько запросов, сколько времени
- любое расхождение объясняется в той же строке, где показано, иначе
  отчёт не выпускается
- если утверждаешь, что работа в ветке — приложи `git log main..HEAD`

Не писать «готово» о том, что не проверено. Проверка — это выполненная
команда с выводом, а не намерение.

### Найдено по ходу: заказы FBO не пишутся с 2026-09-11

Пока сверял строки с БД, оказалось, что `marketplace_orders` для FBO
пуста за 09-11 … 09-13. Логи Render (прочитаны через API, ключ в `.env`):

```
ночь   шаг FBO                                     записано строк
09-10  7 страниц, все 200                              3 656
09-11  429 rate_limit_per_second на offset 0                0
09-12  429 на offset 0                                      0
09-13  1 страница 200, 429 на offset 1000                 508
09-14  3 страницы 200, 429 на offset 3000              1 443
```

Механизм: старый загрузчик обрывался на первом 429 и писал накопленное с
кодом 0 — это загрузчик из списка молчунов (`loader_partial_data_contract.md`,
строка 111). Сортировка ASC, поэтому доезжали только старые даты окна.
В БД по датам: 09-09 fbo=113, 09-10 fbo=7, 09-11 … 09-13 fbo=0. FBS
не пострадал: 09-11 173, 09-12 215, 09-13 236 строк, в логах отказов нет.

Начало совпадает с чатом разработчиков: с 2026-09-11 несколько продавцов
пишут, что методы заказов отдают `rate limit per second` при единичных
запросах («Заказы со вчерашнего дня не отдает», «до этого годами
работала»); 2026-08-31 текст отказа называет `max rate per sec.: 2`.
Ответа Ozon в чате до 09-13 нет. Наш шаг FBO идёт сразу после FBS
(четыре обращения подряд без пауз) — этого стало достаточно.

Новый код: пауза 1,5 с перед каждой страницей, на 429 — 60 с и до трёх
попыток, затем исключение вместо частичной записи. Днём 14-го при таких
паузах 0 отказов на 64 обращения. Если ночью пройдёт, окно в 30 дней само
доберёт 09-10 … 09-14.

**Риск, не решён:** шаг FBO в пайплайне фатальный. Если три паузы по 60 с
не хватит, прогон остановится до расходов, рекламы и KPI. Это развилка,
которую не обсуждали, поэтому не трогал. Варианты: внести шаг в
`NON_FATAL_STEPS` (частичной записи теперь нет, терять нечего) или
переставить FBO после рекламы.
