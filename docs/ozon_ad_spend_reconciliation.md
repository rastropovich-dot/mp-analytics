# Сверка рекламных расходов Ozon с финансовыми операциями

Дата: 2026-09-05. Статус: рабочий документ, пополняется по ходу добора.

## 1. Зачем понадобился независимый контроль

Детектор пропусков (`scripts/ozon_cpc_data_gap_report.py`, затем его переписанная
версия) искал недобор, сравнивая наши же таблицы между собой. Такая сверка
замкнута: она не может поймать случай, когда данные не пришли целиком.

Независимый источник — `POST /v3/finance/transaction/list` Seller API. Он
бесплатный, не входит ни в один лимит Performance API и содержит поле
`operation_type`. Рекламные списания приходят типами:

```
OperationPromotionWithCostPerOrder   — CPO, оба инструмента
ServiceAdvertisement...              — CPC (клики)
```

Финансовая дельта за дату `D = списано по финансам − лежит у нас в
marketplace_expenses`. Это цель добора, вычисленная не из наших витрин.

## 1a. Граница проекта: 2026-03-28

Реклама у Ozon идёт с **2025-09-01**. Данные проекта — `marketplace_expenses`
и `marketplace_orders` — начинаются с **2026-03-28**. Между этими датами семь
месяцев расхода, которого в системе нет:

```
КЛИКИ  208 дат   96 563 954,34 ₽
CPO     82 даты  13 335 689,66 ₽
```

Это **не дефект пайплайна, а граница проекта**. Собирать туда расход нельзя:
за тот период нет ни заказов, ни выручки, и любой отчёт, суммирующий период,
покажет чистый убыток на пустом месте. Заполнение такой «дыры» создаёт новую.

Границу держать явно и проверять по ней все цели добора, иначе она
обнаруживается заново каждые полгода.

### Что осталось внутри границы

## 1b. campaign/product: бесплатный измеритель расхода на грануле кампания+дата

Проверено 2026-09-05 на дате 2026-09-02, чтением, ноль единиц квоты.

Колонки выдачи: `ID`, `Название кампании`, `Статус`, `Тип продвижения`,
`Места размещения`, `Недельный бюджет ₽`, `Расход ₽`, `Показы`, `Клики`,
`Добавления в корзину`, `CTR %`, `Средняя стоимость клика ₽`,
`Продано товаров шт.`, `Продажи в продвижении ₽`, `ДРР в продвижении %`,
`Стратегия`.

**Ни SKU, ни артикула. Гранула — кампания, а не товар.**

Что метод при этом умеет, и умеет хорошо:

```
потолок 1000 строк    снимается при переданных campaignIds
                      (4 046 строк за 45 обращений пачками по 100; в квоту выгрузок не входят)
точность              сумма расхода = списаниям CPC копейка в копейку
глубина               работает как минимум до 2025-10-15 — там тоже
                      совпадает со списаниями, в отличие от отчётов CPO
```

Проверенные даты: 04-02, 05-15, 07-01, 08-13, 10-15-2025 — все сходятся точно.
Исключение: 2026-03-29 расходится на +1 258,93 ₽, причина не выяснена.

**Как этим пользоваться.** SKU в выдаче нет, поэтому заменить
`statistics/json` метод не может — `marketplace_expenses` ключуется через
`marketplace_sku`. Но он даёт то, чего у нас не было: **бесплатный точный
измеритель расхода на грануле кампания+дата на всю историю**.

Отсюда два постоянных применения:

1. **Контроль приёмки платного бэкфилла.** После закрытия даты сверять не
   только с финансами (гранула — дата), но и с `campaign/product` по каждой
   кампании. Финансы ловят недобор по сумме, этот метод — по кампаниям, то
   есть ловит и случай, когда суммы сошлись, а набор кампаний неверен.
2. **Оценка цены бэкфилла.** Объединение кампаний с ненулевым расходом за
   даты окна и есть цена окна в единицах квоты (см. §1d).

## 1d. Цена бэкфилла кликов: 4 944 единицы на 95 дат

Считается по **объединению кампаний в окне**, а не по произведению
«дат × кампаний». Экспорт кампании в окне возвращает её сразу по всем датам
окна: зонд 10 кампаний × 21 день стоил 10 единиц, не 210. Длина периода на
цену не влияет.

Замер 2026-09-05 бесплатным `campaign/product`, кампаний в кабинете 4 496:

```
окно  период                      дат  верх. оценка   ЦЕНА, единиц     ₽ закрывает
W1    2026-03-28 … 2026-05-28      43          1524           1507    1 695 385,64
W2    2026-05-29 … 2026-07-29      38          1241           1237    1 582 249,13
W3    2026-08-02 … 2026-09-02      14          2209           2200    1 322 258,35
ИТОГО                              95          4974           4944    4 599 893,12
```

«Верхняя оценка» — объединение за окно целиком; «цена» — объединение только
за целевые даты окна. Разница ничтожна (30 единиц на всё), то есть почти
каждая кампания окна активна хотя бы в одну целевую дату.

W3 дороже W1 при втрое меньшем числе дат: кабинет рос, кампаний в августе
больше, чем весной.

**Опровергнуто здесь же:** прежняя оценка «303 даты × 483 кампании =
146 349 единиц, задача неосуществима». Она множила цену на число дат, чего
окно не делает. Верная цена для тех же 95 дат внутри границы — 4 944 единицы,
то есть 10–17 ночей порциями по 500 при чистом остатке 300–600 за ночь.

Для сравнения: прежний план на 28 дат стоил 4 323 единицы. Прибавка в
621 единицу покупает ещё 67 дат и 0,92 млн ₽ — почти все кампании уже были в
объединениях.

## 2. Что нашлось

Разрыв по всей истории раскладывается на два инструмента:

```
CPO   ~13,5 млн ₽    ← в 4 раза больше кликов
CPC    ~3,68 млн ₽
```

Сбор CPO бесплатен по квоте Performance API (см. §4), поэтому порядок работ
переставлен: сначала CPO, клики последними.

### 85 дат, сходящихся в ноль

После 2026-05-22 (дата, с которой Selected CPO собирается) 85 дат дают
финансовую дельту ровно ноль. Это независимое подтверждение, что метод сверки
верен, а не подогнан: там, где оба инструмента собраны, расхождения нет.

## 3. Классы дат при доборе

Обозначения: `D` — финансовая дельта, `X` — собранный Selected CPO.

```
X = D    класс A подтверждён, дата закрыта
X < D    класс B: остаток принадлежит CPO «Все товары», это его цель
X > D    НЕ класс B. Дефект: лежащий order_5 завышен или задваивается.
```

Правило: при `X ≠ D` прогон останавливается и показывает дату, `D`, `X`,
разницу. Переклассификация даты по ходу прогона запрещена — это подгонка мерки
под результат.

Разделение на классы построено на признаке «есть ли за дату строки
`advertising_order_5`», а не «полны ли они». Допущение проверяется равенством
`X = D`, а не наличием строк.

## 3a. Возвраты: у операций есть знак

`v3/finance/transaction/list` отдаёт списания **отрицательными**, возвраты —
положительными. Первая версия развёртки брала `abs(amount)` и складывала
возвраты как списания, завышая финансовую сторону и показывая «недобор» там,
где его нет.

За окно 2026-03-01…2026-09-04 возвратов ровно три, все по CPO, на 27 721,60 ₽:

```
2026-08-20   +2 400,65     (operation_id 60974190065)
2026-08-21  +23 548,30     (operation_id 60974189975)
2026-08-22   +1 772,65     (operation_id 60974190066)
```

Номера операций идут подряд — это одна поздняя корректировка, выставленная
задним числом сразу на три даты. Возвратов по CPC нет ни одного.

Критерий сверки поэтому считается **по списаниям**, а возвраты учитываются
отдельно. Приёмка класса A по Selected CPO от этого не пострадала: все 40 дат
сошлись ещё на `abs`, что возможно только при отсутствии возвратов на них.

### Отчёт Ozon ведёт себя на этих датах непоследовательно

```
2026-08-22  отчёт отдаёт СПИСАНИЕ МИНУС ВОЗВРАТ   416 504,50
2026-08-20  при ночном сборе отдавал ДО вычета    427 696,25
            при пересборе 2026-09-05 — те же 5 SKU уже с нулевым расходом
```

Следствие на 2026-08-20: пересбор обнулил пять строк в
`ozon_daily_sku_ad_attribution` (ровно −2 400,65), а в `marketplace_expenses`
те же пять строк остались прежними — `build_cpo_rows` строку с нулевой суммой
не создаёт, поэтому upsert старую не трогает, а `build_cpo_attribution_rows`
такую строку создаёт. Две таблицы за эту дату разошлись на 2 400,65 ₽.

Это **несимметричность двух построителей строк**, а не свойство данных, и
проявляется она на любом пересборе даты, где Ozon убрал строку из отчёта.

### Правило: возврат — событие, а не уменьшение расхода задним числом

Критерий сверки — «наши CPO = списаниям». На 2026-08-20 `marketplace_expenses`
даёт 427 696,25, ровно списания, значит **прав расход**. Испортилась
атрибуция: пересбор обнулил в ней пять строк, и она стала равна «списания
минус возврат». Пять строк восстановлены из снимка 2026-09-05, обе таблицы
снова равны списаниям.

Обнулять строки расхода под сегодняшний отчёт нельзя — это подгонка под
источник, который сам себе противоречит. Возврат фиксируется отдельным
событием. Как учитывать возвраты в витринах — отдельный вопрос, он не решён;
но он не решается молча обнулением строк.

### Дефект: построители строк несимметричны

```
build_cpo_rows              строку с нулевой суммой НЕ создаёт
build_cpo_attribution_rows  строку с нулевой суммой создаёт
```

Поэтому при пересборе даты, где Ozon убрал строку из отчёта, атрибуция
обнуляется, а расход остаётся прежним, и две таблицы расходятся. Сработает на
любом таком пересборе, не только на 2026-08-20.

### Правило: границы периода задаёт источник, а не удобство

За один день граница поиска дважды оказалась нашей, а не дырой в данных:
детектор начинался с 2026-04-02 и прятал 04-01; развёртка начиналась с
2026-03-01 и прятала март целиком.

Любую границу периода берём из источника. Если границу всё же приходится
задать — она называется явно и проверяется отдельно.

Дно проверено 2026-09-05: `v3/finance/transaction/list` отдаёт данные до
**2023-04-28** — это первая операция аккаунта, а не предел выдачи. Помесячная
проба от 2026-02 назад: данные без разрывов до 2023-04, затем четыре пустых
месяца подряд. Ограничения по глубине у метода нет.

## 4. Какие методы не тратят квоту

Лимит `min(активные_кампании × 240, 2000)` расходуется только методом
`POST /api/client/statistics/json`, и считается он в кампаниях-выгрузках:
одна кампания в submit = 1 единица, опросы и скачивание бесплатны, длина
периода на цену не влияет.

Не входят в лимит:

```
GET  /api/client/statistics/all_sku_promo/orders/generate   CPO «Все товары»
POST /api/client/statistic/orders/generate                  Selected CPO (singular!)
GET  /api/client/statistics/externallist                    список выгрузок
GET  /api/client/statistics/campaign/product                CSV, ≥232 дней назад
POST /api/client/statistics/products/sku                    только сегодня/вчера
```

## 4a. Квота Performance: модель окончательная

Источник — страница Limits документации Performance API, приведена владельцем
дословно 2026-09-06. Проверять больше нечего, вопрос закрыт.

```
Одна рекламная кампания = одна выгрузка.
Если в запросе несколько кампаний, это считается как несколько выгрузок.

Лимит на количество одновременных выгрузок с аккаунта            1
Лимит на количество выгрузок за 24 часа с аккаунта            2000
Лимит на количество выгрузок за 24 часа в рамках организации  2000
Лимит на количество одновременных выгрузок по организации        5
Лимит на количество дней в выгрузке                             62
Лимит на количество кампаний в отчёте                           10
Общий лимит на количество запросов в сутки                 100 000
Лимит на количество выгрузок в сутки рассчитывается по формуле:
  количество активных кампаний × 240 — но не больше значения из таблицы
```

### Единица — выгрузка, не запрос

Запросы никогда не были ограничением: мы тратим порядка 600 из 100 000.
Опросы и скачивания значения не имеют, разрежение опроса не нужно.

**Отозвано:** правка 2026-09-06, переписавшая модель на «2000 запросов, опросы
входят». Она опиралась на текст отказа
`{"error":"Превышен дневной лимит запросов (максимум 2000)"}` — неточную
формулировку сообщения, принятую за спецификацию. Вся ветка рассуждений про
«11 запросов на отчёт» и экономию на опросах была ложным следом целиком.

### Два лимита по 2000 — и это объяснение отказов

Одно и то же число стоит на двух уровнях: на аккаунт и **на организацию**.
Значит все кабинеты организации делят общие 2000 выгрузок в сутки, и
посторонний потребитель ест не «чужую» квоту, а нашу.

```
2026-09-05   наших выгрузок 554, отказ
             остальные ~1400 взял кто-то ещё внутри организации
```

Это первое настоящее объяснение отказов за всё время наблюдений.

**Вопрос со вторым ключом закрыт отрицательно.** Ключ внутри той же
организации упирается в тот же потолок 2000. Пробу не ставим.

### Окно скользящее

Дословно «за 24 часа», не календарные сутки. Расход считать за последние
24 часа, а не с полуночи UTC.

### Формула на нас не влияет

`активные_кампании × 240`, но не больше табличного значения. Активных кампаний
у нас сотни, значит произведение всегда больше 2000, и потолок для нас всегда
ровно 2000. К формуле больше не возвращаться.

### Что подтвердилось в нашей конструкции

```
62 дня в выгрузке      — наши окна W1/W2/W3 ровно такие
10 кампаний в отчёте   — наши пачки ровно такие
1 одновременная        — мы и так идём последовательно
```

### В бэклог

С 14 сентября 2026 вводятся лимиты на работу с кампаниями: создание,
копирование, изменение бюджета, добавление товаров, изменение ставок.
Кампаниями мы не управляем, нас не касается.

## 4b. Миграция с /v3/finance/transaction/list (отключение 2026-09-08)

`/v1/finance/accrual/postings`, `/v1/finance/accrual/types`,

### Где используется у нас

```
loaders/ozon_finance_transactions_loader.py:45
loaders/ozon_expenses_loader.py:64
```

Берём из ответа: `operation_type`, `operation_date`, `amount`,
`accruals_for_sale`, `sale_commission`, `items[].sku`, `items[].name`, `posting`.

### Что даёт замена (проверено 2026-09-06)

`by-day` принимает **одну дату строкой**, диапазон не принимает
(`value length must be 10 runes`). Глубина — на всю историю аккаунта: ответ
есть и за 2023-05-01. Постраничность курсором `last_id`.

Состав: `accrual_id`, `date`, `total_amount`, `unit_number`,
`accrued_category` (ITEM|POSTING), `posting.products[].sku` с
`delivery.services[].type_id` и `commission`, `item_fees.fees[].sku`,
`non_item_fee`, `container_fees`. Тип начисления приходит **числом**,
сопоставимым со справочником `accrual/types` (124 типа) — угадывать по
названию больше не нужно.

`accrual/postings` для выгрузки за период не годится: требует список номеров
отправлений (от 1 до 200), то есть это точечный запрос.

Чего нет: `accruals_for_sale` и `sale_commission` отдельными полями — комиссия
теперь внутри `posting.products[].commission`.

### Возвраты: старый метод брутто, новый нетто

```
2026-08-20   Promotion(54) по by-day       425 295,60
             CPO по transaction/list       427 696,25
             разница                         2 400,65 = возврату за эту дату
```

Наш критерий приёмки — «наши расходы = списаниям» — построен на **брутто**.
Новый метод отдаёт **нетто**. Величина расхождения за весь период известна:
три возврата на 27 721,60 ₽ (§3a). **Решение отложено до миграции; критерий
не переписан.**

На остальных проверенных датах (09-01, 07-01, 04-18) методы совпадают до
копейки по обоим инструментам.

## 5. Дефект замещения в marketplace_expenses

`UPSERT_KEY_FIELDS = (expense_date, marketplace_code, marketplace_sku,
expense_type)` — без `campaign_id`. Если запись собрана по части кампаний,
она **замещает** ранее лежавшую строку, а не дополняет её.

Факт, полученный на пробе с записью 2026-08-12: пять существующих SKU-строк
были заменены подмножеством из 10 кампаний, потеряно **6 813,59 ₽**. Проба
откачена полностью, восстановление проверено построчно.

Путь CPO «Все товары» этому не подвержен: `build_cpo_rows` группирует по
`(expense_date, sku, expense_type)` тоже без `campaign_id`, но запрос идёт без
списка кампаний — один отчёт на дату по всему кабинету, частичного набора не
бывает. Плюс встроенная сверка `total_cpo_expense_from_file` против
`distributed_cpo_expense`.
