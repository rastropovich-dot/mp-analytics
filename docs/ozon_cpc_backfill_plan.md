## 1. Идемпотентность — ОТВЕТ: повторный прогон НЕ безопасен

Фактический ключ конфликта проверен в БД:

```
marketplace_expenses_unique_idx
  (expense_date, marketplace_code, marketplace_sku, expense_type)
```

`expense_type` **входит** в ключ. Значит на дате, испорченной дефектом A, повторная
загрузка положит те же деньги как `advertising_clicks`, а старая строка
`advertising_other` останется рядом. Обе суммируются везде, где расход CPC
считается как `clicks + other` — в детекторе `491ed9f` и в
`reports_ozon_ad_diagnostic_rule.py:459`.

Воспроизведено тестом `tests/test_ozon_backfill_idempotency.py`:

```
до загрузки : advertising_other   14 216,52 ₽   -> CPC итого 14 216,52 ₽
после       : advertising_other   14 216,52 ₽
              advertising_clicks  14 216,52 ₽   -> CPC итого 28 433,04 ₽
```

**Что должно произойти со старыми строками до загрузки.** Два рабочих варианта,
оба проверены тестом:

- **Переклассификация на месте** (рекомендуется): `advertising_other` →
  `advertising_clicks` для строк CPC-происхождения. После неё повторная загрузка
  идемпотентна — новая строка перетирает старую по тому же ключу.
- Удаление строк `advertising_other` за дату непосредственно перед загрузкой.
  Проще, но теряет данные, если загрузка не удастся, и не решает проблему для
  остальных 89 дат.

Дополнительно, из того же теста: **upsert никогда не удаляет.** SKU, попавший в
базу при прошлой загрузке и отсутствующий в новой, останется навсегда. Для
`collapsed`-дат это значит, что повторная загрузка добавит недостающее, но не
уберёт мусор, если он там есть.

## 2. Восстановимость — ВЫВОД ОТОЗВАН 2026-09-01

> **Прежняя редакция этого раздела утверждала, что 23 даты невосстановимы,
> потому что кампании до 2026-08-16 исчезли из живого списка. Это неверно.**
> Проверка задачи A опровергла версию. Раздел сохранён с исправлением, а не
> переписан молча, потому что на нём строился весь план.

### Что было измерено неправильно

Мерилась доля кампаний даты, встречающихся в **свежих данных атрибуции**. Это
показывает, какие кампании недавно **тратили деньги**, а не какие **существуют**.
Кампания может жить в списке и просто не иметь расхода. Прокси спутал «нет
свежего расхода» с «удалена», и вывод был построен на этой подмене.

### Что показывают данные на самом деле

Все 147 кампаний с данными за 2026-07-13 имеют ID из блока до пересборки
(27 754 520 – 28 440 282, порог события 35 674 512). Из них 112 строк на
13 854,61 ₽ записаны прогоном **2026-08-31**, то есть через 49 дней после даты и
уже ПОСЛЕ пересборки ID.

Значит на 31 августа живой список **содержал** кампании из старого блока, и
запрос статистики по ним **вернул данные**.

| Утверждение прежней редакции | Статус |
|---|---|
| кампании до 08-16 исчезли из списка | **опровергнуто** |
| 23 даты невосстановимы | **не подтверждено** |
| нужна проба по «мёртвым» ID | **отпадает** — мёртвых ID не обнаружено |

### Фильтруем ли мы что-нибудь сами

Нет. `list_campaigns` отправляет только `advObjectType=SKU`, никакого фильтра по
состоянию не передаётся. Поле `state` используется лишь для приоритизации в
`daily_cpc_priority_key`; из отбора архивные и остановленные кампании не
исключаются. `build_daily_cpc_selection` фильтрует по `is_cpc_campaign` и
пересечению с периодом, но не по состоянию.

Единственное реальное сужение — `ADV_OBJECT_TYPES`, по умолчанию `["SKU"]`:
кампании других типов объектов в список не попадут вовсе. Для CPC это, судя по
всему, верно, но проверено не было.

### Что осталось необъяснённым

**Причина пустоты 2026-07-13 неизвестна.** Известно только, что за дату было
запрошено 1123 кампании, а расход нашёлся у 147, тогда как на соседних датах его
имеют 500–650. Пересборка ID это не объясняет. Версию не заменяю новой: данных
для неё нет.

### Что это меняет в плане

Ограничение на 5 дат снимается — под вопросом снова все 28. Но сроки и порядок
ниже пересчитаны не были, потому что до них стоит блокер §1 (переклассификация),
и пересчитывать их имеет смысл после него.

## 4. Квота и календарь

Текущая выборка — **около 600 кампаний на дату** (не 1123, как было в июле):
`cpc_campaign_count` за 25–31 августа держится в диапазоне 554–642.

Значит одна дата бэкфилла ≈ **600 единиц**.

Бюджет суток:

| Статья | Единиц |
|---|---:|
| Лимит на аккаунт (и на организацию) | 2000 |
| Ночной регулярный прогон | ~600 |
| Необъяснённый расход в момент отказов | ~половина лимита |
| Guard: `--ozon-max-daily-cpc-units` | 1200 на прогон |
| Guard: стоп pre-фазы | `used > 1500` |
| Guard: стоп post-фазы | `used >= 1800` |

Планировать по номиналу нельзя: в момент реальных отказов наши units составляли
31–85% лимита, то есть примерно половину выбирает потребитель, которого мы не
видим. С запасом на это остаётся **400–800 единиц в сутки** на бэкфилл.

**Календарь: одна дата в сутки.** Две по 600 единиц дают 1200 сверх ночных 600 —
это 1800 при лимите 2000 и при неучтённом стороннем расходе гарантированный 429.

- 5 приоритетных дат → **5 суток**.
- Все 28 дат → **28 суток**. После отзыва §2 это снова верхняя оценка объёма.

Выгрузок одновременно — 1, поэтому даты идут строго последовательно, и запускать
надо вне окна ночного джоба (00:15–06:00 UTC).

## 7. Очерёдность с переклассификацией — ПЕРЕКЛАССИФИКАЦИЯ ПЕРВОЙ

Три независимых довода, любого достаточно:

1. **Иначе бэкфилл удвоит расход.** §1: пока строки лежат в `advertising_other`,
   повторная загрузка кладёт вторую копию рядом. Это блокер.
2. **Иначе результат переклассификации нельзя будет проверить.** Сейчас в
   `advertising_other` ровно 1194 строки на 123 413,92 ₽ — известное, фиксированное
   число, с которым сверяется результат. Бэкфилл поверх изменит и суммы, и состав
   строк, и эталона для проверки не останется.
3. **Иначе не снять обходные пути.** Сложение `clicks + other` живёт в четырёх
   местах, включая сам детектор. Пока оно есть, детектор не отличит переклассифи-
   цированную дату от испорченной.

Порядок: **переклассификация → проверка её результата → снятие обходных путей →
бэкфилл.** Для пяти восстановимых дат из §5 переклассификация не блокирует
формально (у `absent`-дат нет строк вообще), но смешивать две операции в одном
окне всё равно не стоит: при расхождении будет непонятно, чей это след.

## 8. Критерий готовности и откат

### Дата закрыта, когда детектор переводит её в `normal`

```bash
python3 scripts/ozon_cpc_data_gap_report.py
```

Единственный критерий. Не `run_status`, не `pending = 0`, не «прогон отработал» —
именно уровень в детекторе. Промежуточные состояния тоже информативны:
`absent → collapsed` означает, что часть данных пришла, и дату надо прогнать ещё
раз; `absent → absent` означает, что не пришло ничего, и повтор бесполезен без
разбора причины.

Снимать показание **до** и **после** каждой загрузки, по одной дате за раз.

### Если стало хуже

«Хуже» — это рост расхода по дате выше медианы соседей (признак задвоения из §1)
или падение уровня относительно снятого до загрузки.

1. **Остановиться и не запускать следующую дату.** Ошибка, повторённая на пяти
   датах, вчетверо дороже в разборе.
2. Сравнить `marketplace_expenses` по дате в разрезе `expense_type` с показанием
   до загрузки. Задвоение видно как две строки на один SKU с разными типами.
3. Отката транзакцией нет: `save_rows` делает upsert без версионирования, и
   прежние значения не сохраняются. Восстановление — только адресным исправлением
   затронутых строк, поэтому **снимок расхода по дате в разрезе `expense_type`
   надо сохранять до каждой загрузки**, иначе откатывать будет не к чему.
4. Причину зафиксировать в этом документе до продолжения.

### Что снять до первой загрузки

```sql
select expense_date, expense_type, count(*) rows, round(sum(expense_amount)::numeric,2) amount
from marketplace_expenses
where marketplace_code='ozon' and expense_date in ( ... даты плана ... )
group by 1,2 order by 1,2;
```
