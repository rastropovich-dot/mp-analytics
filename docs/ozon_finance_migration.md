# Миграция finance API и разрыв ряда расходов

## Что произошло

`POST /v3/finance/transaction/list` и `/v3/finance/transaction/totals`
отключены Ozon **8 сентября 2026**. Проверено в тот же день:

```
/v3/finance/transaction/list  ->  HTTP 400 {"code":9,"message":"obsolete method cannot be used"}
/v1/finance/accrual/by-day    ->  HTTP 200
```

## Почему старое поведение невоспроизводимо

Старый метод отдавал **операцию** с одним `operation_type` на всю операцию.
Новый отдаёт **начисление**, внутри которого услуги разложены построчно, у
каждой свой `type_id`: 182 начисления из 1000 за 2026-09-03 несут по две
услуги разных типов.

Попытка подобрать набор `type_id`, воспроизводящий прежние суммы, проведена
перебором всех подмножеств до шести типов с требованием совпасть на трёх датах
одновременно:

```
logistics   цель  36 600,94 / 20 106,57 / 23 481,90   набор не найден
other       цель  98 836,00 / 52 827,93 / 68 079,74   набор не найден
```

Сумма целых начислений тоже не подходит. Причина: старая величина складывалась
из услуг разных типов внутри одной операции, а соответствия операций и
начислений больше не существует.

**Следствие: разрыв ряда неизбежен.** Выбор был не между «с разрывом» и «без»,
а между честным разбором и подгонкой под невосстановимую цифру.

## Дата разрыва

```
2026-09-08
loaders/ozon_finance_accrual.py: EXPENSES_SERIES_BREAK_DATE
                                 EXPENSES_HISTORY_RECALCULATED = False
```

До этой даты расходы собраны старой логикой, после — новой. **Периоды
несопоставимы, пока не выполнен пересчёт истории.** Сравнивать август с
сентябрём по расходам нельзя.

Утренняя проверка обязана говорить об этом одной строкой, пока
`EXPENSES_HISTORY_RECALCULATED` не станет `True`.

## Как устроен разбор сейчас (шаг первый)

```
commission.sale_commission        -> expense_type "commission"
delivery.services[].type_id       -> по таблице TYPE_TO_EXPENSE
item_fees.fees[].fees[].type_id   -> по таблице TYPE_TO_EXPENSE
type_id 41 (PayPerClick), 54 (Promotion) -> ЯВНЫЙ ПРОПУСК
всё прочее                        -> "unknown_<type_id>"
```

Реклама пропускается намеренно: её источник — Performance API, а витрины
читают `advertising_clicks` и `advertising_order_5`. Если писать её ещё и из
финансов, расход задвоится. Проверено: 0 строк рекламы, 412–447 услуг
пропущено за дату.

В `TYPE_TO_EXPENSE` попадает только то, соответствие чего доказано — сверкой
обоих методов на 161 дате (`data/ozon_finance_migration_parity_20260906.json`)
либо сопоставлением операций со 100 % чистотой. Всё остальное видно как
`unknown_<type_id>` с именем и суммой, а не уходит молча в «прочее».

Витрины `unknown_*` не читают.

## Что НЕ мигрировано

`loaders/ozon_finance_transactions_loader.py` (выкупы) по-прежнему ходит в
мёртвый метод и падает. Не переведён сознательно: выкупы — база расчёта
прибыли, а форма продаж и возвратов в новой модели не разобрана. Писать туда
угаданные числа опаснее, чем день не писать ничего: данные добираются окном в
30 дней, как только загрузчик будет переведён.

## Что дальше

```
1. таблица 124 типов начислений -> классификация владельцем
2. пересчёт истории ОДНИМ действием: новая классификация + знак возвратов +
   перевод unknown в нормальные типы. Разделять нельзя — иначе три разрыва
   вместо одного.
3. после пересчёта EXPENSES_HISTORY_RECALCULATED = True, ряд снова единый
```

Дисциплина пересчёта — как на бэкфилле кликов: снимок, предсказание по каждому
типу и месяцу ДО прогона, приёмка по каждой дате против знаковой суммы
операций, стоп на первой несошедшейся.
