# Миграция finance API и разрыв ряда расходов

## Что произошло

`POST /v3/finance/transaction/list` и `/v3/finance/transaction/totals`
отключены Ozon **8 сентября 2026**. Проверено в тот же день:

```
/v3/finance/transaction/list  ->  HTTP 400 {"code":9,"message":"obsolete method cannot be used"}
/v1/finance/accrual/by-day    ->  HTTP 200
```

## Почему старое поведение невоспроизводимо

Старый метод отдавал **операцию** с одним `operation_type` на всю операцию.
Новый отдаёт **начисление**, внутри которого услуги разложены построчно, у
каждой свой `type_id`: 182 начисления из 1000 за 2026-09-03 несут по две
услуги разных типов.

Попытка подобрать набор `type_id`, воспроизводящий прежние суммы, проведена
перебором всех подмножеств до шести типов с требованием совпасть на трёх датах
одновременно:

```
logistics   цель  36 600,94 / 20 106,57 / 23 481,90   набор не найден
other       цель  98 836,00 / 52 827,93 / 68 079,74   набор не найден
```

Сумма целых начислений тоже не подходит. Причина: старая величина складывалась
из услуг разных типов внутри одной операции, а соответствия операций и
начислений больше не существует.

**Следствие: разрыв ряда неизбежен.** Выбор был не между «с разрывом» и «без»,
а между честным разбором и подгонкой под невосстановимую цифру.

## Дата разрыва

```
2026-09-08
loaders/ozon_finance_accrual.py: EXPENSES_SERIES_BREAK_DATE
                                 EXPENSES_HISTORY_RECALCULATED = False
```

До этой даты расходы собраны старой логикой, после — новой. **Периоды
несопоставимы, пока не выполнен пересчёт истории.** Сравнивать август с
сентябрём по расходам нельзя.

Утренняя проверка обязана говорить об этом одной строкой, пока
`EXPENSES_HISTORY_RECALCULATED` не станет `True`.

## Как устроен разбор сейчас (шаг первый)

```
commission.sale_commission        -> expense_type "commission"
delivery.services[].type_id       -> по таблице TYPE_TO_EXPENSE
item_fees.fees[].fees[].type_id   -> по таблице TYPE_TO_EXPENSE
type_id 41 (PayPerClick), 54 (Promotion) -> ЯВНЫЙ ПРОПУСК
всё прочее                        -> "unknown_<type_id>"
```

Реклама пропускается намеренно: её источник — Performance API, а витрины
читают `advertising_clicks` и `advertising_order_5`. Если писать её ещё и из
финансов, расход задвоится. Проверено: 0 строк рекламы, 412–447 услуг
пропущено за дату.

В `TYPE_TO_EXPENSE` попадает только то, соответствие чего доказано — сверкой
обоих методов на 161 дате (`data/ozon_finance_migration_parity_20260906.json`)
либо сопоставлением операций со 100 % чистотой. Всё остальное видно как
`unknown_<type_id>` с именем и суммой, а не уходит молча в «прочее».

Витрины `unknown_*` не читают.

## Статус нового метода: бета

`/v1/finance/accrual/by-day` **официально считается бетой** (разработчики в
чате Ozon, 2026-09-11: «метод реально ещё считается в бете с кучей
недоработок, но v3 отключили»). Выбора нет — старого метода не существует, —
но полагаться на форму ответа без проверок нельзя: она может измениться.

### Лимиты новых методов не устоялись

2026-09-11 у селлеров ломался `/v1/finance/accrual/types`: один запрос
проходил, дальше «request rate limit per second» на часы. Ozon в 15:38 написал
«поправили». Отказ на новых методах — не обязательно признак нашей ошибки;
нужны ретраи с паузой.

### Часть 429 — антиспам, а не лимит

Поддержка Ozon: «при подозрении на спам система перестаёт принимать запросы на
несколько минут, а после автоматически включает».

Практическое следствие: не всякий 429 лечится уменьшением объёма. Часть
случаев лечится **паузой**, и стратегия «стоп до сброса суточного окна» для них
избыточна — она стоит нам суток там, где хватило бы нескольких минут.
Различать по тексту ответа: `daily_quota_exhausted` — настоящий лимит,
`rate_limit_per_second` и молчаливые отказы подряд — вероятный антиспам.

### Две строки услуги одного типа внутри SKU

Ozon 2026-09-10, дословно: одинаковых SKU внутри начисления не бывает, а две
строки услуги с одним `type_id` внутри одного SKU «теоретически» возможны —
«мы сейчас не отдаём, но явного запрета нет».

Наш разбор суммирует строки, а не замещает, поэтому такой случай выдержит. Факт
фиксируется счётчиком `duplicate_service_line` и строкой в логе: если
«теоретически» станет практикой, мы узнаем в ту же ночь.

Проверено 2026-09-11 на 6 289 начислениях за четыре даты: дублей 0, повторов
SKU 0. Слова Ozon подтверждаются.

## Правило двух суток: начисления доезжают

Сегодняшняя дата недостоверна. Это свойство источника, а не наш запас
прочности, и оно измерено дважды.

**Реклама.** Развёртка от 2026-09-06 не видела за 2026-09-05 ни одной
рекламной операции; сутки спустя за ту же дату стояли 160 900,50 ₽ кликов и
196 411,20 ₽ CPO. Все даты старше двух суток при этом стабильны — расхождений
ноль.

**Расходы.** Приёмка пересчёта 2026-09-11 показала на сегодняшней дате
недобор 13 751,18 ₽. Через полчаса, на том же коде и тех же данных, недобор
вырос до **264 577,62 ₽** — Ozon начислил ещё четверть миллиона, пока шёл
разговор. Для остальных 167 дат расхождений не было ни одного.

Отсюда: **сверка берёт дату не моложе двух суток.** Гнаться за сегодняшней
бессмысленно — она сойдётся сама, когда день закроется.

## Выкупы: форма продаж и возвратов

Переведены 2026-09-11. Продажа и возврат — одно и то же начисление с обратными
знаками во всех полях, отдельного типа операции больше нет:

```
                    ПРОДАЖА        ВОЗВРАТ
sale_amount        +2 751,00      −2 272,00
sale_commission    −1 237,95      +1 067,84
bonus              +1 385,21      −1 191,78
coinvestment            0,00         −10,70
```

Комиссия у продажи отрицательна (удержана), у возврата положительна
(возвращена нам). Знак несёт смысл сам — прежняя конструкция «`abs()` плюс
`sign` по типу операции» здесь не нужна и была бы вредна.

### Соответствие полей

```
старое                      новое
accruals_for_sale           commission.sale_amount
sale_commission             commission.sale_commission (знак инвертирован)
items[].sku                 posting.products[].sku
amount целой операции       sale_amount + sale_commission + услуги доставки
```

Последняя строка выведена фактом, а не догадкой: на 2026-09-07 сумма с
комиссией даёт 2 443 481,77 против 2 421 187,15 в базе, а с услугами доставки —
ровно 2 421 187,15.

### Приёмка

Инвариант, доказанный до разрыва, воспроизведён на трёх датах:

```
             сумма        комиссия     выручка п/к
2026-09-05   +0,00          +0,00          +0,00
2026-09-06   −0,00          +0,00          +0,00
2026-09-07   +0,00          +0,00          −0,00
```

### Количество штук новая модель не отдаёт

У товарной строки ровно три поля: `sku`, `delivery`, `commission`. Поля
количества нет. Старый код считал записи `items[]`, где один SKU мог
встречаться дважды (две моносерьги — две записи), поэтому его число больше:

```
2026-09-05   147 против 149
2026-09-06   203 против 206
2026-09-07   227 против 234
```

Расхождение известно и **не подогнано**: денежные поля сходятся до копейки, а
штуки взять неоткуда. `buyouts_qty` теперь считает позиции, а не единицы
товара. Если количество понадобится точным — искать в другом методе.

## Что дальше

```
1. таблица 124 типов начислений -> классификация владельцем
2. пересчёт истории ОДНИМ действием: новая классификация + знак возвратов +
   перевод unknown в нормальные типы. Разделять нельзя — иначе три разрыва
   вместо одного.
3. после пересчёта EXPENSES_HISTORY_RECALCULATED = True, ряд снова единый
```

Дисциплина пересчёта — как на бэкфилле кликов: снимок, предсказание по каждому
типу и месяцу ДО прогона, приёмка по каждой дате против знаковой суммы
операций, стоп на первой несошедшейся.
