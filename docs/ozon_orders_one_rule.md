# Заказы Ozon в одну сторону: отменённые рядом с подтверждёнными

Ветка `orders-cancelled-columns`, 2026-09-16. Дешёвый путь по решению
владельца: хранить всё, «созданные» и «подтверждённые» — фильтр при
чтении, а не два правила записи. Полная модель (зерно отправление × товар,
`docs/reports_model.md`) не строится — она нужна третьему отчёту, который
всё равно ждёт месяц накопления лога статусов.

Состояние 2026-09-17: миграция применена владельцем (~10:40 UTC), ветка
слита в `main` (`1ca569d`, ~18:50 UTC), первая ночь на новом коде — 09-18.
Скрипты с записью (история) не запускались.

## 1. Схема — `sql/20260916_marketplace_orders_cancelled_columns.sql`

```
cancelled_orders_qty            numeric not null default 0
cancelled_orders_amount_buyer   numeric not null default 0
cancelled_orders_amount_seller  numeric not null default 0
observed_at                     timestamptz                    ← момент сбора, подтвердившего строку
check: все три cancelled_* ≥ 0
```

Ключ прежний: уникальный индекс `(order_date, marketplace_code,
marketplace_sku, order_schema)` — проверено по `pg_indexes` 2026-09-16.
Старые колонки `orders_*` сохраняют смысл «подтверждённые»; читатели
(девять модулей, все берут `orders_qty` и `orders_amount_seller`) не
меняются. Созданные = `orders_* + cancelled_*`.

**Почему две пары колонок, а не строка со статусом.** Строка со статусом
меняет ключ и заставляет каждого читателя фильтровать; две пары на старом
ключе не трогают ни ключ, ни читателей, а «созданные» — одно сложение.
Цена — при появлении третьего исхода (например, «не принят на СЦ» как
отдельная судьба) придётся добавлять третью пару; сегодня такого исхода
нет: у Ozon отмена одна, `cancelled`.

**Дозревание.** Отмена приходит неделями после заказа (срез 09-15: плато
41 % FBO, 38 % FBS к 21-му дню). Ночной сбор строит окно (30 дней)
целиком заново и upsert переписывает обе пары у каждого ключа окна:
заказ, вчера лежавший в `orders_*`, сегодня перекладывается в
`cancelled_*` той же строкой. Upsert это выдерживает, потому что обе пары
всегда пишутся вместе из одного полного сбора; ключ не исчезает —
отменённое отправление остаётся в выборке метода. Отмена позже 30 дней
после заказа (доли процента по срезу) окном не ловится — как и сейчас;
ловить её должен ежемесячный широкий проход (методы принимают период до
года), это отдельное решение.

**Дата — когорта.** `order_date` — дата заказа (FBO `created_at`, FBS
`in_process_at`), не дата отмены. Дату отмены хранит
`ozon_posting_status_log` (наблюдаемая, точность сутки). Поэтому строка
за 09-01 меняется ещё две недели, но остаётся строкой за 09-01.

## 2. Одно правило — `loaders/ozon_orders_rows.py`

Обе схемы зовут одну функцию `build_order_rows(postings, schema)`:

```
статус                          куда
cancelled                       cancelled_orders_*
cancelled_from_split_pending    пропуск, считается вслух (родитель разделённого отправления; товары живут в дочерних)
все остальные из спеки          orders_*
незнакомый                      orders_* И называется вслух (молчаливого else нет)
```

Товарная строка: `sku` (без sku — пропуск и счётчик), `quantity` ≤ 0 —
пропуск и счётчик, цена — строка (`/v3` FBS) или объект `{amount,
currency}` (`/v3` FBO, `/v4` FBS); чужая валюта и объект без `amount` —
исключение, не ноль. Суммы считаются в Decimal, пишутся с округлением
до копейки. Каждая строка несёт `observed_at`.

Что изменилось у загрузчиков:

- FBO: `build_order_rows` больше не выбрасывает `cancelled` — отменённые
  идут в `cancelled_*`; `save_orders` прежний (upsert по старому ключу).
- FBS: статус теперь читается; отменённые в `cancelled_*`, подтверждённые
  в `orders_*`; `quantity or 1` заменено явным правилом (нет количества —
  пропуск и счётчик); окно сбора 14 → 30 дней, как у FBO — иначе отмены
  второй недели не дозревают в таблице.

Тесты: `tests/test_ozon_orders_rows.py` (18), `tests/test_fbs_cursor_migration.py` (10).

## 3. FBS на `/v4/posting/fbs/list`

`/v3/posting/fbs/list` — `deprecated: true`, «с 31 августа 2026 года метод
будет отключён» (спека). Известно по FBO, что Ozon сигналит об отключении
ошибкой лимита `code 8`. Загрузчик переведён по той же механике, что FBO
на `/v3`: cursor, страница 100 (спека `maximum: 100`), пауза 1,5 с между
страницами, на 429 — 60 с и три попытки, предел 400 страниц с падением
вместо частичного результата, любой не-200 — исключение (старый
загрузчик молча возвращал накопленное).

Отличия контракта, проверенные спекой и сырьём: `result.postings` →
`postings + cursor + has_next`; `offset` → `cursor`; страница 1000 → 100;
`products.price` строка → объект `money.postingMoney` (старый
`float(price)` упал бы на первом товаре); `created_at` в `/v4` нет —
дата и раньше бралась из `in_process_at` (заполнен у всех 5 838
отправлений снимка 09-15). Чат разработчиков: в июне `/v4` отдавал не
все отправления и с задержкой (06-01, 06-04), поэтому сверка сделана на
полном 30-дневном окне, а не на четырёх датах — §5.

## 4. Устаревшие ключи FBO — предложение, не сделано

1 108 ключей на 15 778 719,00 за 08-17 … 09-14 (измерено 09-15): заказы,
записанные до отмены и оставшиеся в таблице, потому что старый FBO
выбрасывал отменённые, а upsert не удаляет. С новым правилом таких
ключей больше не возникает: отменённое отправление приходит в сборе и
переписывает свою строку.

Что делать со старыми. Два варианта:

- **пометить** — уже есть бесплатно: `observed_at`. После первой ночи на
  новом коде у всех ключей окна, которые сбор вернул, `observed_at` =
  время сбора; у устаревших он останется `null`. Запрос
  `order_schema='fbo' and order_date >= <начало окна> and observed_at is null`
  и есть их список. Читатели их не различают — «созданные» за август
  останутся завышенными на эти 15,8 млн;
- **удалять в окне сбора** — после каждого полного сбора удалять ключи
  схемы за полные локальные дни окна (с первого дня + 1 по последний),
  которых нет среди построенных строк. Условие безопасности — «полный
  сбор»: оба загрузчика уже падают вместо частичного результата (предел
  страниц, 429 после трёх попыток, любой не-200), поэтому до удаления
  дело доходит только при полном списке. Первый день окна не трогать: он
  неполон по UTC-границе.

Предлагаю второе, но не в этой ветке: включать удаление стоит после
первой чистой ночи на новом коде и после пересборки истории (§6) — она
сама снесёт все устаревшие ключи за окно с 03-28, так что нужда в
удалении останется только на будущее (ключи, чья дата сдвинулась:
`in_process_at` у FBS появляется позже создания, в снимке 09-15 таких
нет). Удаление сейчас — отдельная правка `save_orders`/`save_ozon_orders`
с тестом «удаляем только после полного сбора».

## 7. Порядок включения

1. Владелец применяет миграцию (§1) — колонки с default 0 читателям не
   мешают, старый код на `main` продолжает писать как писал.
2. Мерж ветки в `main` → Render катит автоматически → первая ночь:
   оба загрузчика пишут обе пары; FBS впервые на `/v4` и на 30 днях.
3. Утром: в логе Render строки `Ozon FBO: отправлений подтверждённых …,
   отменённых …` и то же для FBS; в таблице
   `sum(cancelled_orders_qty) > 0` за вчера по обеим схемам;
   `observed_at` у строк окна = время сбора.
4. Пересборка истории (§6) — по слову владельца, после чистой ночи.
5. Удаление устаревших ключей (§4) — отдельная правка, после истории.

Обратный путь: миграция не удаляет и не переименовывает — откат ветки
возвращает старую запись, лишние колонки остаются с нулями.
