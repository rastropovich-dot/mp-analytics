# Миграция загрузчиков заказов на курсорные методы

`/v2/posting/fbo/list` и `/v3/posting/fbs/list` помечены `deprecated: true`
с датой отключения **31.08.2026**. Дата прошла, оба метода на 2026-09-13 ещё
отвечают — но на это полагаться нельзя: `/v3/finance/transaction/list`
переносили дважды и отключили ровно в объявленный срок.

Замены: `/v3/posting/fbo/list` и `/v4/posting/fbs/list`.

## Три отличия контракта

```
                      старое                  новое
постраничность        offset                  cursor
верхний уровень FBO   result: []              postings: [] + cursor + has_next
верхний уровень FBS   result.postings: []     postings: [] + cursor + has_next
размер страницы       1000                    100        ← в именах полей не видно
```

Третье отличие нашлось только на живом вызове: параметр `limit` есть в обеих
версиях, но у новых стоит `maximum: 100`
(`posting.v3.PostingFboListRequest.limit`, `posting.v4.PostingFbsListRequest.limit`).
**Страниц станет вдесятеро больше**, и это надо закладывать вместе с частотным
лимитом.

## Сверка, 2026-09-13 (этап 1, db_writes = 0)

Сравнивались МНОЖЕСТВА `posting_number` в обе стороны, а не количество: при
потерянной странице и лишних дублях количество совпало бы.

Код: `scripts/posting_api_parity.py`.

### FBO — чисто

```
дата          старый  новый  уник ст  уник нов  стр ст  стр нов
2026-08-06       485    485      485       485       1        5   ✅
2026-09-05       148    148      148       148       1        2   ✅
2026-09-08       151    151      151       151       1        2   ✅
2026-09-10       168    168      168       168       1        2   ✅
```

2026-08-06 взята как самая крупная дата августа: курсор перелистнул пять
страниц и собрал ровно то же множество, что старый метод за одно обращение.
Это и была главная проверка перехода со смещения на курсор.

### FBS — множества сошлись, поля отличаются

```
дата          старый  новый  уник ст  уник нов  стр ст  стр нов
2026-08-06       275    275      275       275       1        3
2026-09-05       218    218      218       218       1        3
2026-09-08       244    244      244       244       1        3
2026-09-10       212    212      212       212       1        3
```

**В `/v4/posting/fbs/list` нет поля `created_at`** — подтверждено живым ответом
и спекой (`posting.v4.PostingFbsListResponse.Postings`, 40+ полей, `created_at`
среди них нет).

Наш загрузчик FBS его **не читает**: дата берётся из `in_process_at` или
`shipment_date` (`loaders/ozon_fbs_orders_loader.py:101`), оба поля в новой
версии есть. Для FBS это не поломка, а неточность проверки — список полей был
общий для обеих схем, по образцу FBO, где `created_at` читается.

Поймать стоило: если бы `created_at` читался, переключение молча испортило бы
дату заказа.

### Поля, которые читают загрузчики

```
FBO   posting_number, status, created_at, in_process_at, products
      products: sku, offer_id, name, quantity, price
FBS   posting_number, status, in_process_at, shipment_date, products
      products: sku, product_id, offer_id, name, quantity, price
```

Все присутствуют в новых версиях, кроме `created_at` у FBS, который FBS и не
читает.

## Частотный лимит

За один сеанс сверки дважды получен `429 code 8` «request rate limit per
second» — на вызовах подряд без пауз, ретраев `http_retry` (потолок 10 с) не
хватило. Помогла выдержка **60 секунд**, ровно как описывает поддержка Ozon про
антиспам. Первое живое подтверждение этого правила на Seller API — раньше оно
было записано только для Performance.

Из этого следует требование к переключению: **пауза между страницами в самом
загрузчике**, выдержка 60 с и не более 3 попыток на 429, предел страниц с
падением вместо частичного результата.
