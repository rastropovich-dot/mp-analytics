Проект 2026-09-15 (одиннадцатая задача). Только проектирование и измерение:

## 1. Откуда модель: ручной отчёт и его коэффициенты

Владелец считал финрез руками (`data/manual_report_july.xlsx`, вне git).
Формулы лежат в ячейках; прочитаны через `openpyxl` с `data_only=False`.

**Выкупы — факт, один коэффициент (НДС):**

```
Выручка        = (Оборот − Комиссия с НДС) / 1,22
Маржа          = Выручка − Себестоимость
Мар-ть %       = Маржа / Выручка
% Логистики    = Логистика / Выручка
% ДРР (от ТО)  = Реклама / Оборот                 ← от оборота, не от выручки
% Эквайринга   = Эквайринг / Выручка
Фин. рез.      = Маржа − Логистика − Реклама − Эквайринг − Прочее
```

**Заказы — прогноз, три зашитых коэффициента:**

```
ДРР        = Реклама / (Выручка × 0,65 × 1,22 / 0,59)
Фин. рез.  = Маржа × 0,65 − Реклама − Выручка × 0,65 × 0,024
```

`0,65` — выкупаемость, `0,59` — доля после комиссии (комиссия 41 %),
`0,024` — прочие расходы. Коэффициенты дрейфуют молча: на листе «Выкупы —
Ozon Селект» (с 01.12.2025) ДРР = `H/(B*1,2/0,72)` — НДС 20 % и комиссия
28 %. Ряды разных периодов несопоставимы, и увидеть это можно только в
формуле.

**Решения владельца, на которых стоит модель:**

1. зашитых коэффициентов не будет — выкупаемость, комиссия, доля прочих
   измеряются;
2. храним всё, отмены не выбрасываем: «созданные» и «подтверждённые» — это
   фильтр при чтении, а не два правила записи;
3. оба загрузчика чинятся в одну сторону — записывать статус и факт отмены;
   FBO сейчас неправ (молча выбрасывает `cancelled`, оставляя в таблице
   ключи, которые никто не подтверждает), FBS ближе к «созданным» (пишет
   всё), но статуса не хранит.

   расхождение с ручным отчётом по СС (их цены выше на 16 % в сентябре)

## 2. Зерно хранения — отправление × товар

**Предложение: один факт = одна товарная строка одного отправления.**

```
ozon_posting_lines
  posting_number        text      ключ, часть 1   (65330751-0093-1)
  sku                   bigint    ключ, часть 2
  order_number          text      номер заказа (одно на несколько отправлений)
  schema                text      fbo | fbs
  platform              text      main | select | discount — по префиксу offer_id F / S / T
  offer_id              text      артикул как в кабинете; offer_id_norm = lower()
  quantity              integer
  price                 numeric   цена за штуку из products[].price (/v3 FBO — объект {amount}, читать amount)
  order_date            date      день заказа по МСК: FBO — created_at; FBS — in_process_at (created_at в /v4 нет)
  ordered_at            timestamptz исходная метка
  status                text      последний известный статус Ozon (awaiting_… / delivering / delivered / cancelled)
  substatus             text
  is_cancelled          boolean   status = cancelled
  cancel_reason_id      integer   FBO: поле отправления; FBS: cancellation.cancel_reason_id
  cancel_reason         text
  cancellation_type     text      client | seller | … (у FBS ещё cancelled_after_ship, affect_cancellation_rating)
  cancelled_at_observed timestamptz когда МЫ впервые увидели cancelled — см. §3, даты отмены у Ozon нет
  cancel_date           date      день отмены по МСК, производная от cancelled_at_observed
  delivered_at_observed timestamptz когда впервые увидели delivered (аналогично)
  warehouse_name, city, payment_type_group_name — из analytics_data, справочно
  first_seen_at, last_seen_at, source_snapshot — служебные
```

Почему это зерно, а не строка «дата × SKU» или «отправление»:

- три отчёта и все срезы — фильтры и группировки над одной таблицей; по
  отправлению × товару агрегируются и «созданные» (все статусы), и
  «подтверждённые» (без `cancelled`), и любой срез — без отдельного
  хранения, значит без расхождений между ними;
- ключ `(posting_number, sku)` стабилен: отмена — это **обновление статуса
  той же строки**, а не исчезновение ключа. Сегодняшняя болезнь FBO
  (ключ «дата × SKU» остаётся без отправлений и никем не удаляется)
  исчезает по построению: нечему оставаться;
- себестоимость и категория цепляются по `offer_id` (99,99 % выручки),
  площадка — по префиксу (100 %), реклама — по SKU (99,1 %) — все три
  признака есть на этом зерне и не требуют доп. таблиц;
- сегодняшняя `marketplace_orders` (дата × SKU × схема) становится
  представлением над этой таблицей — читатели KPI не меняют контракт.

Альтернатива «строка заказа плюс отдельная таблица отмен» рассмотрена:
она оставляет отмену событием в другой таблице, и для «подтверждённых»
нужен join на каждом чтении; при этом отмена всё равно должна изменить
строку заказа (статус), иначе строка заказа «не знает», что отменена.
Отдельная таблица оправдана только для **истории переходов** (§3), не для
факта отмены.

## 3. Две даты — ключевое, и одной из них у Ozon нет

**Дата заказа** есть у обоих схем (`created_at` у FBO, `in_process_at` у
FBS). **Даты отмены нет ни в одном ответе Seller API.** Проверено 09-15 по
спеке и по сырью:

- `/v3/posting/fbo/list`: 15 полей, из дат только `created_at`,
  `in_process_at`; `cancellation` = {`cancel_reason`, `cancellation_type`,
  `cancellation_initiator`}, `cancel_reason_id` — без времени;
- `/v4/posting/fbs/list`: 44 поля, даты `in_process_at`, `shipment_date`,
  `delivering_date`, `pickup_code_verified_at`; `cancellation` = {…,
  `cancelled_after_ship`, `affect_cancellation_rating`} — без времени;
- `/v2/posting/fbo/get`, `/v3/posting/fbs/get` — `fact_delivery_date` есть,
  даты отмены нет;
- по всей спеке поле «дата отмены» встречается дважды и оба не про наше:
  `cancelled_at` у заявок на условную отмену (`/v2/conditional-cancellation/list`,
  только FBS и только заявки) и `cancelled_with_compensation_moment` у
  возвратов;
- начисление типа 6 `Cancellation` как прокси не годится: в начислениях
  1–9 июля таких строк ноль.

**Решение владельца 2026-09-15: наблюдаемая дата отмены = дата первого
сбора, в котором статус стал `cancelled`.** Точность — сутки: сбор ночной,
отмена в 01:00 МСК и в 23:00 МСК лягут в один день наблюдения. Колонка
зовётся `cancelled_at_observed` / в логе `observed_at` — это **момент нашего
сбора, а не момент отмены у Ozon**; тот, кто читает, обязан это знать.
Реализация — лог переходов статусов (`ozon_posting_status_log`,
`sql/20260916_create_ozon_posting_status_log.sql`), пишется из тех же
ответов, что ночной сбор уже получает.

Возможные уточнения, не сейчас: (а) собирать чаще раза в сутки — точнее
и дороже; (б) для FBS-заявок брать `cancelled_at` из
`/v2/conditional-cancellation/list` — покрывает только часть отмен;
(в) `fact_delivery_date` для доставленных — есть в `get`, но не в `list`.

**Два взгляда — два запроса над одной таблицей:**

```
по дню заказа      group by order_date;  created = все строки; confirmed = where not is_cancelled
                   день никогда не окончателен: дозревает неделями (§5)
по дню отмены      group by cancel_date; where is_cancelled
                   день закрывается сразу, но смешивает свои заказы с чужими отменами
```

История переходов (для кривой дозревания, §5, и для проверки самого себя):

```
ozon_posting_status_log
  posting_number, status, substatus, observed_at     ключ (posting_number, observed_at)
```

Одна строка на каждое изменение статуса, замеченное сбором. Из неё
кривая дозревания считается продольно, а не срезом.

## 4. Три отчёта поверх одной модели

```
1. Заказы созданные        всё, что создано в день D              — как в оригинале
2. Выкупы                  факт из начислений (marketplace_buyouts) — как сейчас, база прибыли
3. Заказы с дозреванием    созданные(D) − отмены(D), известные к моменту расчёта
                           − ожидаемые отмены(D) по кривой дозревания
```

Третьего отчёта в оригинале нет: там 0,65 применяется ко всем дням
одинаково. У нас свежая дата получает прогноз по своему возрасту, а
закрытая — факт.

**Формулы, оригинал / наша модель:**

```
                     оригинал                                   наша модель (все величины измерены, ни одной зашитой)
Оборот               сумма заказов дня (созданных)              Σ price × quantity по строкам дня, по срезу
Комиссия             Оборот × 0,41 (заказы) / факт (выкупы)     факт: sale_commission из accrual по выкупам;
                                                                для прогноза — измеренная доля за окно, не 0,41
НДС                  / 1,22                                     параметр с датой действия (vat_rate, valid_from), не константа в формуле
Выкупаемость         0,65                                       кривая дозревания c(age) по схеме/площадке, §5
Прочие               Выручка × 0,024                            факт по типам accrual (`other`, `subscription`, `external_promo`)
Реклама              со Standard, без разнесения                Performance по SKU → площадка по префиксу (99,1 % расхода)
ДРР от оборота       Реклама / Оборот                           то же; плюс ДРР от подтверждённого оборота — отдельной колонкой
```

Определение: `c(a)` — доля отменённых среди отправлений возраста `a`

Два снимка FBO с разницей в 31 час дали одну кривую — срез устойчив.

день на 0–1 сутки видит лишь четверть своих будущих отмен.

Продольная проверка: между снимками 75 из 3 770 неотменённых (1,99 %)
стали `cancelled` за 31 час — 60 из `delivering` (невыкуп при доставке),
15 из ожидающих; возраст отменившихся — от 0 до 17 дней. Это и есть
причина, по которой прогноз по кривой нужен даже для двухнедельных дат.

Что нужно для продольной кривой: `ozon_posting_status_log` с первого
ночного сбора после внедрения; кривая по когортам станет доступна через
~30 дней после него (когда первая когорта дозреет), срез — сразу.
**Лог включён 2026-09-16:** посев 6 321 + 541 + 5 838 = 12 700 строк из
снимков 09-14 и 09-15 (владелец, числа сошлись с предсказанием до строки),
ветка слита в `main` (`200e2ea`), первая ночь — 09-17. С этого дня кривая
считается продольно по когортам `order_date`; первая когорта дозреет
(~30 дней) к середине октября, до тех пор действует срез выше.

**Кривая в листе «Заказы» — с 2026-09-21, по переходам, а не срезом** (двадцать
восьмая задача, `scripts/ozon_orders_forecast.py`). Лог статусов сверен с
`marketplace_orders` до рубля на 29 датах по обеим схемам. По каждой паре
соседних ночей (N, N+1) меряется `h(k)` — доля живых (не отменённых)
отправлений возраста `k`, отменённых к следующей ночи, по отправлениям и по ₽;
возрасты сложены в те же вёдра, что в таблице выше. Доля подтверждённых
сейчас, которая ещё отменится: `r(a) = 1 − Π (1 − h(k))`, `k = a … 20`; день
от 21 суток — факт. Это та же величина, что `(c∞ − c(a)) / (1 − c(a))`, но
измеренная внутри когорты.

Формула среза (`c(a)` по молодым заказам, плато по старым) **в прогноз не
идёт — проверено и отвергнуто на данных 09-21:** она смешивает когорты с
разным уровнем отмен. У FBS по ₽ плато (возрасты 21…29, заказы конца августа)
вышло 31,2 %, а молодые сентябрьские заказы к 6-му дню уже на 31,9 % — срез
обещал «отмен больше не будет» с шестого дня, тогда как переходы показывают
ещё 16,5 %. Срез считается и лежит справочно на листе «Кривая дозревания».

Рублёвая кривая ниже штучной на всех возрастах (FBO на 1-е сутки: ещё
отменится 24,3 % ₽ против 33,8 % отправлений) — дорогие заказы отменяют реже,
поэтому к рублям применяется рублёвая, к штукам — штучная. Рублёвая шумит
хвостом цен: на 09-21 одна отмена FBS на 665 028 ₽ на 20-е сутки — 15,5 %
всех ₽ отмен в переходах; вес падает с каждой ночью (складываются последние
45 ночей). «Продольной версии к середине октября» ждать не нужно: кривая
строится заново каждое утро из всего лога.

**Подтверждённые ≠ выкупленные** (найдено там же): за апрель … август выкупы
954,0 млн при подтверждённых заказах 1 009,2 млн — 94,5 %; по месяцам 84–105 %
(сдвиг даты заказа к дате реализации). Остаток ~5 % — гипотеза: возвраты после
доставки, отменой не считаются. В листе «Заказы» такого коэффициента нет —
прогноз фин. реза по заказам выше выкупного на эту долю.

Сырьё `data/postings_raw/` на Render не сохраняется между прогонами
(у cron-задачи нет постоянного диска): лог пишет из файлов того же
прогона, архива сырых списков в проде нет. Если он понадобится — хранить
в таблице (raw jsonb) или на внешнем диске, отдельное решение.
