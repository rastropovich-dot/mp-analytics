## Сравнивать можно только созданные

Под новым правилом `orders_*` из файлов с `orders_*` в базе сравнивать нельзя:
в базе — созданные, в файлах — подтверждённые. План сравнивает **созданные =
подтверждённые + отменённые** против `orders_* + cancelled_orders_*` базы
(`stored_dates` складывает обе пары, поэтому сравнение верно и до, и после
записи). По каждой группе план печатает: строк станет / в базе, созданных,
подтверждённых, отменённых (шт и ₽), новые ключи (дата, SKU), ключи «в базе есть,
в сырье нет».

## Две защиты от «восстановления» мусором

1. **Чужие даты.** Строки не той даты в дне — день не трогается. Проверка стоит и
   при съёме сырья (такой ответ в файл не кладётся), и при чтении файла.
2. **Пустой ответ.** Пустой день там, где в базе лежат заказы, — не истина «ноль»:
   так выглядит и горизонт, и сбой WB. При съёме — отказ без файла, в плане —
   «нет файла сырья», поимённо.

Плато с дырой коридором не проверить — запись отказывает, пока дата не снята или
отказ не принят явно (`--accept-out-of-corridor`, только после разбора).

## Витрины

Ключей `daily_sku_kpi` по WB на 176 датах — 31 670 (23 046 с заказами, 8 624 —
выкупы без заказов); пересчёт полный и перепишет все. Новых ключей на плато —
ноль на всех измеренных датах: осыпание режет ячейку (дата, SKU), но не убивает
её. Ключей без источника восстановление не создаёт: только upsert, удалений нет.
Значения `orders_*` по WB в витрине упадут примерно вдвое — это смена базы, не
потеря: `docs/wb_orders_write_window.md`, «Правило записи».

## Прерываемость

Прогресс — `logs/wb_orders_history_restore_progress.json`, пишется после каждой
записанной даты; повторный запуск берёт с места обрыва. Из файлов весь прогон —
секунды, так что обрыв маловероятен, но коридор на продолжении не проверяется
(в очереди уже не всё плато) — об этом печатается строка.

```
--from-files DIR        дни из файлов сырья; основной путь
--plan                  показать план и выйти, ни одного запроса к WB
--max-dates N           взять N дат за прогон
--date-from/--date-to   ограничить диапазон
--retry-failed          повторить даты, на которых был отказ
--restart               забыть прогресс и начать сначала
--accept-out-of-corridor  писать при приросте вне коридора — только после разбора
```

Без `--from-files` скрипт по-прежнему умеет ходить в WB по дню на запрос (65 с
пауза), но тогда горизонт режет очередь, и `--newest-first` вреден.

## Порядок запуска

```bash
python3 scripts/wb_flag1_raw_capture.py --out logs/wb_flag1_raw --date-from <первая неснятая> --date-to <вчера − 30>
python3 scripts/wb_orders_history_restore.py --from-files logs/wb_flag1_raw --plan
# --- слово владельца по числам плана ---
python3 scripts/wb_orders_history_restore.py --from-files logs/wb_flag1_raw --approve-wb-orders-write
python3 reports_daily_sku_kpi.py
python3 reports_daily_marketplace_kpi.py
```

Снимок KPI перед пересчётом берётся отдельно, как 2026-09-03
(`snapshots/kpi_before_20260903_meta.json`).
