# Заказы WB: окно записи (D) и ремонт по flag=1 (C)

> Измерения 2026-09-03, только чтение. Код готов, но НЕ выкачен.
> Механизм осыпания — `docs/wb_data_integrity.md` §1.

## Ключевое измерение: почему окно вообще работает

`flag=0` отбирает по дате последнего изменения. Для даты **внутри** окна
`dateFrom = today − N` ответ полон по построению: `lastChangeDate >= order_date`,
и раз дата заказа попала в окно, то и дата изменения тоже. Для даты **старше**
окна приходит только изменившаяся часть — её и записывает upsert поверх полного дня.

Проверено, а не выведено:

- В ночном ответе `flag=0` (4780 строк, `dateFrom = 2026-08-04`) **нет ни одной
  строки** с `lastChangeDate` раньше даты заказа.
- **2026-08-10**, возраст 24 дня, у края окна: `flag=1` — 218 строк, тот же день
  внутри ночного `flag=0` — 218 строк, **множества `srid` совпали полностью**.
  В базе лежит 218.
- **2026-08-25**, возраст 9 дней: `flag=1` — 48 строк, в базе 47. Единственная
  разница — заказ, изменившийся сегодня в 17:23 UTC, то есть **после** ночного
  прогона. Это обычное отставание на несколько часов, не осыпание.

Внутри окна замещать день целиком — правильно. За окном — это и есть порча.

## Что даёт вариант D

`loaders/wb_orders_loader.py`: пишем только `order_date >= today − N`.
Строки старше окна не выбрасываются молча — считаются и печатаются в лог.

На ночном ответе 2026-09-03 это отделило бы **28 дат** (`2026-07-03 … 2026-08-03`,
1310 строк ответа) от 31 даты внутри окна. Именно эти 28 дат сейчас
переписываются каждую ночь.

Замечание к масштабу порчи. Разница «что лежит в базе» против «что записала бы
эта ночь» по этим 28 датам — **ноль**: база уже равна вчерашнему огрызку.
Осыпание не накапливается по чуть-чуть, оно каждую ночь приравнивает день к
текущему объёму изменений, а тот с возрастом падает. Поэтому «остановить рост
порчи» = «перестать писать за окно», без вариантов частичного смягчения.

## Выбор N: 30 дней, и это следует из данных

Мерили не «сколько живёт заказ», а прямо: **на какой возраст приходятся
изменения**. Запрос `flag=0` за 7 суток, 631 строка, из них 445 с
`lastChangeDate > date` — то есть настоящие изменения задним числом:

| лаг изменения | доля полосы | накопленно |
|---|---:|---:|
| 1–7 дней | 18,9 % | 18,9 % |
| 8–14 дней | 34,1 % | 53,0 % |
| 15–21 день | 33,5 % | 86,5 % |
| 22–25 дней | 9,2 % | 95,7 % |
| 26–30 дней | 3,1 % | **98,9 %** |
| больше 30 дней | 1,1 % | 100 % |

Хвост за 30 днями — пять изменений за восемь суток: лаги 32, 36, 36, 46 и 51
день. Все пять — отмены (`isCancel = true`; отмены вообще составляют 280 из 445
изменений).

Отсюда:

- **N = 30** ловит 98,9 % изменений и не требует менять запрос — окно запроса
  уже 30 дней. Это и выбрано.
- N = 45 или 60 подняло бы охват до ~100 %, но потребовало бы расширить запрос
  (`dateFrom` = today − 45), а вместе с ним вырос бы объём ответа и время шага.
  Выигрыш — единицы отмен в месяц. Не стоит того, тем более что вариант C
  подбирает их вообще без окна.
- N = 2–3 дня (как предлагалось в §4 `wb_data_integrity.md`) **хуже**: он
  выбрасывает не 1,1 % изменений, а 92 % (изменения с лагом
  больше трёх дней), и перекладывает их на ремонт — это 20+ запросов за ночь вместо одного-двух. Окно записи должно быть равно окну
  запроса, а не меньше него.

### Что теряем при N = 30 — прямым текстом

Изменения заказов старше 30 дней перестают доходить до базы. Практически это
**поздние отмены**: 5 штук за 8 суток наблюдения, то есть порядка **0,6 отмены
в сутки**, около 19 в месяц. Их эффект односторонний: история будет слегка
**завышена** — заказ, отменённый на 40-й день, останется в дате как заказанный.

Это ровно тот размен, ради которого D и делается: −19 отменённых заказов в месяц
против −14 600 заказов, уже осыпавшихся. Плюс вариант C возвращает и эти 19.

## Вариант C: ремонт flag=1, и во сколько он обходится

`scripts/wb_orders_repair.py`. Детектор — один запрос `flag=0` за последние
26 часов; всё, что старше окна записи и всплыло в нём, чинится запросом `flag=1`
на дату и перезаписывается целиком.

Сколько дат за ночь реально трогается — измерено по тем же 445 изменениям,
разложенным по дню изменения:

| ночь | тронуто дат всего | из них старше 30 дней |
|---|---:|---:|
| 2026-08-27 | 14 | 0 |
| 2026-08-28 | 16 | 0 |
| 2026-08-29 | 20 | 0 |
| 2026-08-30 | 24 | 0 |
| 2026-08-31 | 28 | **3** |
| 2026-09-01 | 25 | 0 |
| 2026-09-02 | 23 | **1** |
| 2026-09-03 | 22 | **1** |

Итого: **21,5 даты за ночь** трогается вообще, но внутри окна их чинить не надо —
их пишет загрузчик. К ремонту остаётся **0–3 даты, в среднем 0,6**.

**Цена ночи: 1 запрос детектора + 0–3 запроса ремонта ≈ 1–4 минуты** при лимите
statistics-api ~1 запрос в минуту. Это укладывается в ночное окно без разговоров.

Отдельно — **первый** прогон: за 26 часов виден не весь хвост. Если запустить
детектор с `--since-hours 720`, целями станут все 28 дат из ночного ответа
2026-09-03, то есть ~28 запросов ≈ полчаса. Разумнее не делать этого вовсе:
исторические даты закрывает `scripts/wb_orders_history_restore.py`, а детектор
пусть с самого начала работает по суточному окну.

### Ограничители в скрипте

- запись только по `--approve-wb-orders-write`, по умолчанию `db_writes = 0`;
- `--max-dates 10` — потолок на прогон, чтобы очередь не съела ночное окно;
- если `flag=1` вернул строки чужих дат — день не трогаем вовсе (проверка на
  случай, если смысл параметра у WB изменится);
- SKU, которые есть в базе, но которых нет в ответе `flag=1`, по умолчанию
  **не удаляются**, только сообщаются: `upsert` их не тронет. Удаление — явным
  `--delete-stale`.

## Правило записи: как у Ozon (2026-09-21)

До 2026-09-21 `orders_*` у WB были **созданные** заказы — каждая строка ответа,
включая отменённые. У Ozon с 2026-09-17 те же колонки — **подтверждённые**, отмены
лежат в `cancelled_orders_*`. Одно имя значило разное. Теперь правило одно
(`loaders/wb_orders_rows.py`, им строят строки загрузчик, ремонт и восстановление):

```
orders_qty / orders_amount_*                      isCancel = false
cancelled_orders_qty / cancelled_orders_amount_*  isCancel = true
observed_at                                       момент сбора
```

Созданные = подтверждённые + отменённые, ничего не выбрасывается; ключ и дата
(когорта заказа, не дата отмены) прежние. Решение советника 2026-09-21, в линию
с решением владельца 2026-09-15 «храним всё со статусом» (`docs/reports_model.md`
§1). Личное подтверждение владельца — перед мержем.

**Что увидит читатель после выкатки.** На ночном ответе 2026-09-21 внутри окна
(08-22…09-21): создано 1 005 шт / 30 960 564 ₽, из них отменено 426 / 15 387 708 —
**42,4 % штук, 49,7 % рублей**. На столько `orders_*` по WB упадут в первую же
ночь, а `cancelled_*` заполнятся; на истории (пробы 04-02…07-21) отменённых 51 %
штук. Для `daily_sku_kpi` / `daily_marketplace_kpi` это смена базы, как у Ozon
2026-08-19: выкупаемость и ДРР по WB вырастут скачком без единого нового события.
Утренний алерт при этом берёт заказы WB из funnel-overlay
(`docs/wb_funnel_consumers.md`), а funnel считает созданные — алерт и витрина
разойдутся ещё сильнее, чем сейчас. До восстановления истории ряд WB разорван
на границе окна записи: внутри окна — подтверждённые, старше — созданные.

**Деньги — Decimal.** Суммы копились во float, в базе лежит
`5258633.509999999995` (08-05). Теперь копятся в Decimal и один раз округляются
до копейки. Отсутствующее поле цены, `None` и не-bool `isCancel` — отказ сборки,
а не ноль и не «подтверждённый по умолчанию». На 9 658 строках сырья 09-21 все
три цены и `isCancel` присутствуют всегда, `priceWithDisc` и `finishedPrice` ни
разу не ноль, копеек больше двух знаков нет.

> **Следствие для ночи.** Шаг «WB: загрузка заказов» в `run_daily_pipeline.py`
> **фатальный** (его нет в `NON_FATAL_STEPS`), а загрузчик теперь умеет падать.
> До мержа шаг надо сделать нефатальным — иначе одна кривая строка WB уносит
> расходы, рекламу и KPI обеих площадок. Файл общий, правка не в этой ветке.

### Что WB называет `isCancel`

**Документация** (dev.wildberries.ru → Отчёты → `GET /api/v1/supplier/orders`,
прочитано 2026-09-21), дословно: `isCancel` — «Отмена заказа: true — заказ
отменен»; `cancelDate` — «Дата и время отмены заказа. Если заказ не был отменен,
то "0001-01-01T00:00:00"». Отмену до отгрузки и отказ при получении документация
**не различает** — установить по ней нельзя.

**Данные** (29 дат сырья `flag=1`, 7 298 заказов, 3 538 отмен): у неотменённых
`cancelDate` всегда `0001-01-01`, у отменённых — всегда дата (время всегда
00:00:00, то есть точность — день). Лаг от заказа до отмены:

| лаг | отмен | доля |
|---|---:|---:|
| в день заказа | 1 228 | 34,7 % |
| 1–2 дня | 636 | 18,0 % |
| 3–7 дней | 1 061 | 30,0 % |
| 8–14 дней | 356 | 10,1 % |
| 15–21 день | 208 | 5,9 % |
| 22–30 дней | 44 | 1,2 % |
| больше 30 | 5 | 0,1 % |

47 % отмен приходят на третий день и позже, 17 % — позже недели; 3 098 отмен из
3 538 — по заказам со склада WB. Отмена на второй-третьей неделе плохо похожа на
«передумал до отгрузки» (сроки отгрузки мы не мерили — это довод по смыслу, а не
по данным). **Гипотеза, документацией не подтверждена:**
`isCancel` покрывает и отказ при получении / невыкуп на ПВЗ. Правило записи от
ответа не зависит; зависит чтение: `cancelled_orders_*` у WB — это «не выкуплено
по любой причине», а не «отменено до отправки».

Там же в документации: «Информация о заказе хранится 90 дней с момента
оформления» — практика расходится, `flag=1` отдаёт 190 дней
(`docs/wb_data_integrity.md` §1); «Данные обновляются раз в 30 минут»; «1 строка
= 1 заказ = 1 сборочное задание = 1 единица товара»; лимит — 1 запрос в минуту.

## Порядок выкатки

1. D (окно записи) — останавливает рост порчи, ноль новых запросов.
2. C (ремонт) — отдельным шагом пайплайна или руками; ставить **после** шага
   загрузки заказов.
3. Восстановление истории — `docs/wb_history_restore_runbook.md`, только после 1.
4. Убрать funnel-overlay из утреннего алерта — `docs/wb_funnel_consumers.md`.
