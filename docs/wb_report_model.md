## 0. Что в листе у владельца (как есть)

Блок «Выкупы WB», строки 4–34, колонки A–S. Формулы владельца:

```
D  Комиссия %   = C / B                              ← 0,42 на всех днях: C — константа 42 % от B
E  Выручка      = (B − C) / 1,22 − [свод]!AB{r+1}     ← вычет «НДС за возмещение», 1…21.09 = 88 946,47
G  Маржа        = E − F
P  Фин. рез.    = G − I − K − M − O
R  Ebitda       = P − $T$81                           ← T81 = 74 002,00 в день
```

Числа (B, C, F, I, K, M, O) — вбиты; I, M, O — с хвостом `/1,22`, то есть
пересчитаны из сумм с НДС. Итоги 1…21: оборот 16 667 220,00, комиссия
6 994 883,75, выручка 7 839 198,00, СС 5 943 927,07, логистика 207 256,16,
реклама 0, эквайринг 332 324,01, прочее 65 971,76, фин. рез. 1 289 718,99,
Ebitda −264 323,01 — как в задаче, сверено с файлом.

## 1. Источник — детализация отчёта реализации

`POST finance-api /api/finance/v1/sales-reports/detailed` (`13-finances.yaml`):
тело `{dateFrom, dateTo, limit ≤ 100 000, rrdId}` — пагинация по `rrdId` (последний
из ответа → в следующий запрос, до `204`), `period: weekly|daily` (по умолчанию
weekly — отчёты за неделю понедельник…воскресенье, `reportId`, `dateFrom`,
`dateTo`, `createDate`). **Лимит 1 запрос в минуту.** Данные доступны с
**2024-01-29** — проверено: запрос от 2024-01-29 с `limit 1000` вернул строки
отчёта `reportId 251047423` за 2024-01-29…02-04, `min rrDate = 2024-01-29`,
`orderDt` с 2023-12-28. Неделя 1…7 сентября — **5 979 строк, 12,1 МБ, 200**, два
отчёта (835101460: 09-01…09-06, 841839787: 09-07…09-13).

Зерно — строка операции (`rrdId`): `nmId`, `vendorCode` (наш артикул, в
нижнем регистре: `f000283615`), `techSize`, `srid`, `shkId`, `sellerOperName`
(«Обоснование для оплаты»), `docTypeName` («Продажа» / «Возврат» / пусто),
`bonusTypeName`, три даты и ~90 полей сумм. Операции за неделю: Возмещение за
выдачу и возврат товаров на ПВЗ 2 595, Возмещение издержек по перемещению и
операционной обработке товара 1 878, Доставка 1 114, Продажа 277, Штраф 102,
Хранение 7, Возврат 4, Компенсация скидки по программе лояльности 2.

**Дата реализации у владельца = `rrDate` («Дата операции»)**, не `saleDt` и не
`orderDt`: штраф 2 560 у отчёта `saleDt` 09-01 / `rrDate` 09-02 — в листе он в
09-02; хранение 2 791,75 с `rrDate` 09-01 — в листе 09-01. По продажам `saleDt`
и `rrDate` внутри недели совпадают, поэтому оборот сходится и так и так.

Это же = `priceWithDisc` из `supplier/sales` = `marketplace_buyouts.buyouts_amount_seller`: 1…21.09 — 16 667 220 в базе и в листе |

По `saleDt` ближе (−421…+487), но тоже не ноль. Правило отнесения у владельца не установлено — гипотеза: другая дата (день доставки) или иной отчёт кабинета |

## 4. Себестоимость: артикулы WB в снимке 1С

`supplierArticle` WB = базовый артикул (`F000287741`), размер — отдельно в
`techSize` (`'0'`, `'17'`, `'17,5'`, `'45'` …). В снимке `offer_id` — вариант
`артикул-размер` (`F000287741-17,5`, запятая как в WB) или без размера для
безразмерных; у одного артикула 8–20 вариантов, и **себестоимость по размерам
разная** (`F000287741`: 14 765,41 … 19 903,50; `T000066064`: 34 343,77 …
59 717,50), `unit_cost_uniform` — одна на артикул (17 414,44 и т. д.).

Покрытие выкупов WB за 1…21 сентября (486 строк, 257 артикулов, 586 позиций,
оборот 16 667 220):

| стыковка | артикулов | оборот | доля |
|---|---:|---:|---:|
| точное совпадение `lower(article)` = `offer_id_norm` (только безразмерные) | 119 из 257 | 4 117 385 | 24,7 % |
| базовый артикул есть в снимке (любой вариант) | **225 из 257** | **15 765 032** | **94,6 %** |
| базового артикула в снимке нет | 32 | 902 188 | 5,4 % |

Значит СС считается по варианту `vendorCode + techSize` (оба есть в каждой строке
отчёта реализации и в `supplier/sales`), с откатом на `unit_cost_uniform` там, где
варианта нет; из `marketplace_buyouts` этого не собрать — размера нет.
Себестоимость владельца 1…21 — 5 943 927,07 (35,7 % оборота); по нашему снимку и
позициям без размера не сравнить, сравнение — после загрузчика. Снимок 05-20;
владелец считает по своим ценам 1С («на 16 % выше нашего снимка» у Ozon,
`cost_of_goods.md`).

## 6. Лента заказов и `isCancel` (задача §3)

`POST /api/analytics/v1/order-feed` (`11-analytics.yaml`): период ≤ 31 дня **по
времени текущего статуса** (`updatedAt`), 1 запрос/мин, пагинация `offset` +
`snapshotTime`. Поля: `srid`, `nmId`, `chrtId`, `createdAt`, `updatedAt`, `status`
∈ {created, buyout, cancel, return, returnDefective}, **`cancelType` ∈ {`app` —
отказ до получения, `receipt` — отказ при получении, `expire` — истёк срок
получения, `other` — техническая отмена}**, `sellerPrice`, `isMp`, `isB2b`.

**Лента различает.** 09-15 (по времени статуса): 49 заказов — cancel 21, buyout
18, created 10; из 21 отмен **`receipt` 15, `app` 4, `expire` 2**. То есть
`isCancel` в `supplier/orders` покрывает и отказ до получения, и отказ при
получении, и истёкший срок — гипотеза 09-21 подтверждена данными ленты (71 %
отмен дня — отказ при получении). На `cancelled_orders_*` это ложится так:
правило записи не меняется (все четыре типа — отмена); чтобы разложить отмены по
типу, нужен join `srid` → `cancelType` из ленты и три-четыре новых счётчика (или
одна колонка `cancel_type` в логе, как `ozon_posting_status_log`) — отдельная
задача, глубина ленты 31 день по времени статуса.

## 7. План пятой задачи — предложение

1. **Загрузчик отчёта реализации** `loaders/wb_sales_report_loader.py`: недели по
   `rrDate`, пагинация `rrdId`, 65 с между запросами, сырьё в
   `data/wb_sales_report_raw/<reportId>.json`; таблица **`wb_sales_report_rows`**
   с зерном `rrdId` (миграция — владелец): ключевые ~30 полей (`rrDate`, `saleDt`,
   `orderDt`, `nmId`, `vendorCode`, `techSize`, `srid`, `sellerOperName`,
   `docTypeName`, `bonusTypeName`, `quantity`, `retailPriceWithDisc`,
   `retailAmount`, `forPay`, `ppvzReward`, `rebillLogisticCost`, `deliveryService`,
   `acquiringFee`, `paidStorage`, `penalty`, `additionalPayment`, `deduction`,
   `paidAcceptance`, `vw`, `vwNds`, `cashback*`). Объём: ~6 тыс. строк/неделю, с
   2026-03-26 — ~150 тыс.; upsert по `rrdId` идемпотентен. Ночной шаг —
   нефатальный, окно 3 недели назад (отчёт за неделю появляется в понедельник
   после неё: `createDate` 09-07 для 09-01…09-06) — 3–4 обращения за ночь.
2. **Витрина/лист** `scripts/report_wb_month.py` по образцу `report_ozon_month.py`:
   колонки §2 из `wb_sales_report_rows` по `rrDate`; комиссия — **две строки**:
   «как у владельца» 42 % (для `--check`) и факт `B − forPay`; СС — по
   `vendorCode + techSize` из `article_unit_costs` с откатом на `unit_cost_uniform`;
   `--check` против листа владельца: B, AB, M, O — до копейки, I — с показом
   разницы, C — обе версии.
3. **Открытое, к владельцу до кода:** комиссию в нашем листе брать фактом
   (44,4 %) или его константой (42 %); правило логистики (наше `deliveryService`
   расходится с его числами до 1,5 тыс/день); чем объясняются 09-03 / 09-07
   эквайринга и +563,20 «прочего» 09-02; нужен ли новый снимок 1С для WB.
4. **Прав токена — не нужно**; таблица — миграция по слову.
