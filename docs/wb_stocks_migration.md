# Остатки WB: переезд на stocks-report

> Проверка 2026-09-03 живыми read-only запросами. Код готов, НЕ выкачен, в базу
> ничего не писалось. Предыстория — `docs/wb_data_integrity.md` §3.

## Что проверено

`POST seller-analytics-api.wildberries.ru/api/analytics/v1/stocks-report/wb-warehouses`
текущим ключом, без смены токена:

| проверка | результат |
|---|---|
| пустое тело `{}` | HTTP 200, 2821 строка |
| `limit` / `offset` | работают: `offset=5` вернул ровно строки 6–10 полного ответа |
| страницы по 1000 | 1000 + 1000 + 821, сумма сходится |
| охват | 1474 nmId, из них 989 с ненулевым остатком, всего 5569 единиц |
| прогон разбора целиком | `wb_stocks_loader --dry-run` → 1474 строки для `stock_daily`, `db_writes = 0` |

## Поля ложатся на stock_daily так

| stock_daily | откуда | комментарий |
|---|---|---|
| `stock_date` | дата прогона | как и раньше, снимок «на сегодня» |
| `marketplace_sku` | `nmId` | размеры (`chrtId`) схлопываются: в ключе `stock_daily` размера нет |
| `warehouse_name` | `warehouseName` | сейчас всегда «Склад WB», см. ниже |
| `stock_qty`, `available_qty` | `quantity` | сумма по размерам, как раньше |
| `reserved_qty` | 0 | как раньше; в ответе резерва нет |
| `article`, `product_name` | **`sku_catalog`** | в ответе этих полей нет вообще |

Проверка на живом ответе: 1474 строки, набор ключей строки совпадает с колонками,
которые заполнял старый загрузчик, — тест `test_rows_match_stock_daily_columns`.

## Две вещи, которые надо знать до выкатки

### 1. Разбивки по складам в ответе НЕТ

Все 2821 строка приходят с `warehouseId = -999999`, `warehouseName = "Склад WB"`.
Это агрегат по всем складам WB. Пробовали `groupByWarehouse`, `warehouseIds`,
`currentPeriod` — эндпоинт **молча игнорирует незнакомые поля**: ответ совпал с
ответом на пустое тело байт в байт (md5 `c0cebd2d`). Соседний путь
`stocks-report/seller-warehouses` существует и отдаёт 204 (своих складов у
продавца нет), `stocks-report/products/products` — 404.

Это расходится с §3 `wb_data_integrity.md`, где разбивка по складам записана как
имеющаяся. По факту её в этом ответе нет.

До 2026-07-14 в `stock_daily` лежало **55 складов** на дату. После переезда будет
одна строка на SKU. Следствия:

- разрез «по складам» через границу 07-14 сравнивать нельзя;
- ключ `(stock_date, marketplace_code, marketplace_sku, warehouse_name)` не
  ломается — просто одно значение вместо 55;
- разбор написан так, что настоящая разбивка, если она появится или найдётся в
  документации, разъедется по строкам сама, без правок кода
  (`test_real_warehouses_split_into_separate_rows`).

**Нужна страница документации.** dev.wildberries.ru отдаёт 498 на автозапрос;
если владелец пришлёт текст раздела, я проверю, есть ли параметр разбивки, и
доведу за один запрос.

### 2. sku_catalog больше нечем пополнять

Старый эндпоинт отдавал `supplierArticle`, `subject`, `brand`, `category`,
`barcode`, и тот же загрузчик писал их в `sku_catalog`. В новом ответе этих полей
нет. Сейчас артикул и название берутся **из** `sku_catalog`, покрытие —
**1360 из 1474 nmId**; у 114 SKU артикул будет пустым, и это печатается в лог
отдельной строкой, а не проглатывается.

Чем это грозит: `reports_sku_decision_daily_input` агрегирует остатки в том числе
**по article**, и SKU без артикула в этот разрез не попадут.

Отдельная задача: пополнять `sku_catalog` из Content API
(`/content/v2/get/cards/list`). В этот переезд не входит.

## Восстановим ли провал с 2026-07-14

**Нет. Остатки исторически недоступны.**

- Отчёт — снимок «на сейчас». Тело с периодом (`currentPeriod`) он игнорирует:
  ответ на запрос с периодом совпал с ответом без периода **побайтово**.
- Параметра даты в ответе нет вовсе: ни поля с датой, ни версии среза.
- Старый эндпоинт, который мог бы отдать прошлое, снят с эксплуатации и отвечает
  404 с уведомлением.

То есть 51 день (2026-07-15 … 2026-09-03) остаётся дырой навсегда. Записывать
сегодняшний срез задним числом в пропущенные даты **нельзя**: это не данные, а
выдумка, и она будет неотличима от настоящих замеров.

Что это значит для витрин: любые расчёты «остатки на дату» и оборачиваемость по
WB на этом промежутке не восстановятся. Как только загрузчик выкачен, накопление
пойдёт заново с текущего дня.

## Ограничения и режим

Лимит — 1 запрос в 20 секунд (в коде пауза 21 с и повтор с той же паузой: штатный
`http_retry` ждёт не больше 10 с, для этого эндпоинта мало). До 250 000 строк,
offset-пагинация. Сейчас данные помещаются в 3 страницы, то есть шаг занимает
около минуты.

`python3 loaders/wb_stocks_loader.py --dry-run` — прогон без записи.

## Тесты

`tests/test_wb_stocks_report.py`, 15 тестов: схлопывание размеров, сохранение
нулевых остатков, совпадение набора колонок со `stock_daily`, артикул из каталога
и пустой артикул без падения, разъезд по настоящим складам, пагинация и остановка
на короткой странице, возврат частичных данных при отказе, и отдельно — что
пустой ответ считается провалом шага, а не зелёной ночью.
